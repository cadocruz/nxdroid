# Porting a Switch title: agent guide

These pages are for an agent asked to analyse a Switch NSP and port it with the native-execution approach of this repository and [d2r-mobile](https://github.com/jhaizhou-ops/d2r-mobile): the game's own aarch64 code runs natively on the device, a rewriter patches only the instructions the platform cannot run, the host replaces Horizon system services, and NVN is replayed on Vulkan (on Android; the Metal replay, `nvn_mtl.m`, stays as the reference it is checked against).

Everything here was learned on Diablo II: Resurrected (SDK ~12, NVN 53, the original target of d2r-mobile) and Super Mario Bros. Wonder (SDK 16.2.0, NVN 55, this repository; its update 1.2.1 uses SDK 16.2.12), then extended by Fire Emblem Engage (Unity, SDK 12.3.7), Metroid Dread (MercurySteam's engine, SDK 11.4.3) 13 Sentinels: Aegis Rim (Vanillaware's engine, SDK 11.4.3, the same `sdk` and movie module as Dread) Super Mario 3D World + Bowser's Fury (Nintendo EPD's sead / agl engine, SDK 10.4.0, NVN API 53) The Legend of Zelda: Breath of the Wild (EPD's sead / ksys engine, SDK 20.5.22, `DT_RELR` relocations, update 1.9.0), The Legend of Zelda: Link's Awakening (Grezzo's engine on NintendoWare, SDK 8.2.0, lower-left window origin) Hyrule Warriors: Age of Calamity (Koei Tecmo's KTGL, SDK 9.6.0, RDB archives, shaders as GLSLC outputs) Super Mario Galaxy (a Wii game on NERD's Hagi layer: recompiled PowerPC code, SDK 18.3.5, Vulkan with SPIR-V generated at run time, a 2.9 GB bss), Ace Attorney Investigations Collection (Unity 2022.3 IL2CPP, SDK 17.5.3: the C# file API through the SDK's C library), and the bring-up of Octopath Traveler 0 (Unreal Engine 5, SDK 19.3.13: an AES-encrypted pak, Oodle-compressed shaders that the game's own code decodes in the host's tool mode, its allocator replaced by the host's). Where titles differed, each is given; the next title will differ again, so treat every number below as "measure it, don't assume it".

## Ground rules

- **Bring your own files.** Keys, NSPs and anything extracted from them stay in the game's work folder (`$W` = `<NSP folder>/<title>-work`, next to the NSPs on the user's external drive; the home folder is nearly full), never in the repository, never in a commit, never printed. Print key *names* and lengths only.
- **Measure, then change.** Each fix in this repository started from a concrete observation (a crash address and its decompilation, a census over all shaders, a memory profile). Write the evidence into the code comment next to the fix, the way the existing code does; the next title will need it.
- **Find the root cause; don't just work around it.** A crash, hang or wrong picture is finished when its root cause is found and fixed there, not when it stops showing. Follow the bad value back to where it was written and the call back to the semantics the host gets wrong; a stub, skip, clamp, retry or timeout that only makes the symptom go away is a workaround, kept only when the root cause cannot be fixed and recorded as open ([AGENTS.md](../../AGENTS.md)).
- **One repository, one profile per title.** nxnative (first called smbw-mobile) started as a copy of d2r-mobile's generic parts. Title- or SDK-specific constants live in the game profile `dm/games/<id>/` ([dm/games/README.md](../../dm/games/README.md)). That covers program ID, known builds, modules, address-space partition, NVN driver tables, the shader tables and the app identity. The code reads the profile through `game_profile.h` (host) or `dm/games/game.py` (tools). Behaviour that fits only one title's code is gated by that title's build ID (`dm_main_build()`), never left on for every title. Some things are still built into the translator: the texture / sampler handle bases and the depth mode (see [04](04-graphics.md)). `dmsh_build.py` refuses a profile whose bases differ from the translator's.
- **Write code comments in English**, and start log lines that mark something unimplemented or wrong with `[RED] `.
- **Test where it runs.** The Android app (`com.nxdroid`, `libdm.so`) on the device is the only target; a compile, a desktop smoke run or a text check is not a device run. Never claim something works on the device without running it there, and say which it was.

## Checklist for a new title

1. Run `scripts/build_ipa_from_nsp.py --survey-only` on the title's NSP folder. With no profile for its title ID, it extracts only the code modules plus a RomFS list and writes `<NSP folder>/<title ID>_survey/survey.md`:
   - modules and build IDs, SDK version and components, engine and graphics API markers;
   - RomFS containers;
   - the rewrite-site census and imports vs. host hooks.

   A 32-bit ARM program (`main.npdm` with the 64-bit instruction flag clear: Pikmin 3 Deluxe, New Super Mario Bros. U Deluxe) stops the survey with a red line: the native-execution approach has no translator for 32-bit ARM code.

   For a provisional profile, `python3 dm/games/profile_guess.py <ExeFS dir> <romfs_manifest.tsv | RomFS dir>` prints the keys the game's files decide, each with its reason: the static keys follow rules checked against every profile, the rest are guesses or defaults ([dm/games/README.md](../../dm/games/README.md)); the run-time keys (`render_cond`, `tex_flush_upload`, `core_preempt`, …) are the bring-up's to find. A profile kept outside the repository is found through `DM_GAMES_DIR` until it moves into `dm/games/`.
2. Extract base (and update, if in scope) — [01](01-extract.md). Finish the survey — [02](02-survey.md). Write down: SDK version, NVN API version, module list, imports the host lacks, SVCs, instruction census, NVN loader pattern, shader containers.
3. Add a game profile `dm/games/<title ID>/game.tsv`, named after the base game's title ID (start from `010015100B514000/game.tsv`: identity, `build` rows, `modules`; keep the memory / NVN values until they are measured) and build the APK for it with `-PdmGame=<id>` ([06](06-dev-loop.md)).
4. Run the rewriter (`patch_nso.py --target=android`, which `prepare_game_android.py` does) and check its counts against `insn_census.py`.
5. Boot on the device and iterate ([03](03-bringup.md)) until the game reaches its frame loop: look up each failure in the [symptom index](symptoms.md), which leads to its entry in the [subsystem references](../reference/README.md).
6. Extract and translate the shaders, find the binding layout by census, and get the first frame — [04](04-graphics.md).
7. Input and audio; then play through and read the `dm` log for `[RED]` lines and the `NVN PERF` numbers ([05](05-debugging.md#on-device-diagnostics)).
8. For a game update: extract it over the base game, diff the imports, carry the per-build addresses over, and rebuild the shader tables for both versions ([01](01-extract.md)).
