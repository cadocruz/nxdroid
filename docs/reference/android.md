# Android: the vendored Vulkan engine

The Android port keeps the game's own AArch64 code and replaces the Metal replay (`dm/gfx/nvn/nvn_mtl.m`) with a Vulkan one. The replay engine and its `nvn_vk.c` adapter are not written here: they are vendored from [jhaizhou-ops/d2r-mobile](https://github.com/jhaizhou-ops/d2r-mobile) (MIT), a fork of this repository, at commit `1e0e7934c9ccdf95494aee5065d1d07ab3cc3918` (tag `v2.1.0`, committed 2026-10-28). The host is wired into CMake (`dm/android/CMakeLists.txt`), its platform primitives adapted behind `dm/host/port.h` and `dm/android/port_android.c`, and the engine compiles and initializes out of tree against our headers ([The desktop smoke build](#the-desktop-smoke-build)); an NDK compile of the host and a device run on the S23 Ultra have not been run yet.

The import of 108 files keeps upstream paths so that a new upstream commit diffs mechanically:

| Path | Files | What it is |
|---|---|---|
| `dm/gfx/vulkan/` | 85 | The Vulkan replay engine and the `nvn_vk.c` adapter that implements this repository's `mtl_*` ABI (`dm/gfx/nvn/nvn_mtl.h`, `dm/gfx/nvn/nvn_obj.h`) |
| `dm/android/compat/` | 13 | Mach, `mach_absolute_time`, QoS, `clonefile`, CommonCrypto and malloc-zone shims for bionic |
| `dm/android/docker/` | 2 | The pinned Linux build environment (Ubuntu snapshot, NDK 29.0.14206865, CMake 3.31.6, Gradle 9.8.1, JDK 17) |
| `dm/android/` | 5 | `CMakeLists.txt`, `front_android.c`, `tools/asm_elf.py`, `vulkan_present.cpp`, `vulkan_present.h` |
| `dm/gfx/nvn/` | 2 | `nvn_copy_pitch.h` (copy stride and extent validation shared by the engine's copy paths) and `nvn_pool_flags_registry.h` (bounded host pool-flags lookup) |
| `dm/gfx/xtrace.h` | 1 | System timeline markers: HiTrace on HarmonyOS, empty elsewhere |

`dm/gfx/vulkan/INTEGRATION.md` (upstream's Chinese integration memo) and `dm/android/jni_android.c` (the D2R app shell: its Java activity, its `/sdcard/Download/S2X/...` data path, its 18 `.data` archives) are deliberately not imported. The imported engine has no title-ID branches; its one title-shaped piece is `xbg_game.cpp`'s camera-patch namespace (it recognises the main camera's constant blocks by content and skips one cull shader by key), which is off unless `DM_CAM` is set. Every imported file, its upstream commit, its sha256, its license and its local modification are recorded in `dm/tools/android_vendor.tsv`.

## The target device, measured

The target is a Galaxy S23 Ultra (`SM-S918B`, Snapdragon 8 Gen 2 for Galaxy, Adreno 740), Android 16 (SDK 36, security patch 2026-09-05), 12 GB. `dm/gfx/vk/probe/vk_probe.c` answers what the backend needs to know from the device itself, prints one `key = value` per line and is validated by `dm/gfx/vk/probe/tests/test_probe_output.py`, which is the contract (42 checks: dotted array indices, `driver_version` with three or four components plus `driver_version_raw`, three decimals on float limits, `device_selected`, an optional `exec_pages_errno`, `driver_info` exempt from the path and timestamp rules). Built for Android with `podman run --rm --userns=keep-id -v "$PWD:/src:rw" -w /src dm-android-tools:1 make -C dm/gfx/vk/probe android NDK=/opt/android-sdk/ndk/29.0.14206865` (`ANDROID_API ?= 24`: the NDK has no `libvulkan.so` stub below it), pushed with `adb push … /data/local/tmp/vk_probe`, run in `adb shell`, and the dump validated with `python3 dm/gfx/vk/probe/tests/test_probe_output.py <dump>`. On the device it is valid and byte-identical across runs.

## The pin and the gate

### `android_vendor.py --check` fails: a vendored file no longer matches its row

- **Symptom:** CI or a local run prints `[RED] android_vendor: <path>: sha256 … does not match the manifest (…)`, or `… is vendored but not in the manifest (run --write)`, and exits 1.
- **Cause:** the bytes under a vendored root changed, a file was added or removed there, or a row drifted from the pin in `dm/tools/android_vendor.py` (`UPSTREAM`, `COMMIT`, `TAG`, `DATE`). The manifest is the only record of what was imported: a changed byte without a changed row means the tree no longer describes its own provenance.
- **Fix:** read the diff first, then either restore the upstream bytes or (for a deliberate local change) run `--write` and put the reason in that row's `modifications` column; the tool keeps an existing row's metadata and only fills new rows. Updating upstream means changing `COMMIT`/`TAG`/`DATE`, running `--write`, and classifying every changed row as *take* (bug fix or driver knowledge), *skip* (specific to upstream's title) or *adapt* (touches this repository's ABI), with the reason in the commit message. Eleven rows carry adapted files in `dm/tools/android_vendor.tsv` (the CMake build, front end, WSI presentation, port layer, Apple stubs, opcode handlers and ABI gaps in `xbg_game.cpp` and `nvn_vk.c`).
- **Found on:** the `v2.1.0` import; `python3 dm/tools/android_vendor.py --check` is the gate and `dm/tools/tests/test_android_vendor.py` drives it on a synthetic tree.

The tool scans the three vendored roots recursively plus the five explicit `dm/android` files, so a new file under `dm/android/compat/`, `dm/android/docker/` or `dm/gfx/vulkan/` cannot be added silently. A file elsewhere under `dm/android/` is out of scope until it is listed in `FILES`. A sha256 does not cover the mode bit, so the one file that is executable upstream, `dm/android/docker/build.sh` (775), is checked separately; a copy that lost `+x` fails.

## The portability audit

`dm/tools/android_audit.py` answers "is this file portable to Android?" for the code the port moves: the C, Objective-C and assembly of `dm/host` and `dm/gfx/nvn`. It prints one line per finding — `path:line: category: text`, grouped by file and sorted — in four categories: `apple-api` (the Mach kernel and Darwin libc: `mach_*`, `vm_*`, `<mach/*>`, `getsectiondata` and `_mh_execute_header`, `os_unfair_lock`, `dispatch_*`, the `pthread_*_qos_class*` calls, `sysctl`, `clonefile`, CommonCrypto, `<TargetConditionals.h>` and `TARGET_OS_*`, `<libkern/*>`, `os_proc_available_memory`, Darwin's ucontext register layout, and an `mrs` of `tpidrro_el0` / `tpidr_el0`: a thread layout, [below](#the-guest-thread-slots-assumed-darwins-tsd-layout)), `objc-framework` (an Apple framework header, an `@`-keyword, an `NS*`/`CF*`/`MTL*`/`GC*`/`CM*`/… type or `id<protocol>`), `page-assumption` (a `16384`, `0x4000`, `1 << 14` or `16 KiB` literal on a line that also talks about a page, `mmap`, `mprotect` or `getpagesize`: a candidate, because the same literal is also used for guest and device constants) and `macho-section` (`section("__DATA,swhle")`, `__TEXT,__text`, `-sectcreate`).

`dm/tools/android_audit_baseline.tsv` is the record of what is Apple-specific today, keyed by file, category and the sha1 of the whitespace-normalised line, so reformatting a file or moving a hit does not invalidate it. `--check`, the command CI runs, fails on a hit that is not in the baseline **and** on a baseline row whose hit is gone: the list only shrinks. `--summary` prints the counts per category and the ten files with the most hits, `--json` one object per hit, `--all` also scans `dm/gfx/metal` and `dm/gfx/vk` for the report. Out of scope, by rule: the vendored trees (`dm/third_party`, `dm/gfx/vulkan`), the probe and the engine smoke harness, and every `tests/` directory — another repository's code, or diagnostics that are not shipped.

### The host's platform primitives live in `dm/host/port.h`

The first bring-up step took the four Apple APIs the audit found most isolated and gave the host one neutral name for each, in `dm/host/port.h`: `dm_clock_ns()` (the monotonic clock that stops in sleep; `now_ns()` in `hle_os.c` is it, and `nvn_dirty.c` reads it in the fault path), `dm_sleep_until_ns()` (an absolute-time sleep: `hle_nvn.c`'s present pacing), `dm_clone_tree()` (the save transaction's whole-tree clone in `hle_fs.c`), `dm_sha256*` (one-shot and streaming over an opaque context: the NRO lookup in `hle_ro.c`, the shader program key in `hle_nvn.c`, the capture in `nvn_capture.inc`) and `dm_qos_set_self` / `dm_qos_self` / `dm_qos_boost_start` / `dm_qos_boost_end` (`hle_thread.c`'s guest-thread classes and the `ArbitrateLock` priority lend, `nvn_rec.h`'s worker threads). On Apple the header defines them inline over CommonCrypto, `clonefile`, `mach_wait_until` and the pthread QoS and override calls, so no unit test links another object and the Metal path is unchanged (`loader.c`'s `DM_LOADHASH` digest and `nvn_mtl.m`'s present threads, prebuild stamp and GPU-timestamp clock go through the same names); on bionic they are `dm/android/port_android.c`, over `dm/android/compat/` (the clone is compat's copy, the digest compat's `digest.c`, the classes compat's nice mapping) and POSIX (`clock_nanosleep` with `TIMER_ABSTIME`). The boost, which Apple's `pthread_override_qos_class_start_np` gives and compat did not declare at all (`hle_thread.c` would not have compiled), is composed there by a lend table: a thread holding lends has an entry with its own class as the base and one bit per active lend in each class, the effective nice is the lowest of the base and the highest lend, and it is re-applied, under the table's mutex, when a lend starts or ends or the owner sets its own class (a refused class leaves the base as it was). Covered by a probe over mocked nice values, not yet on a device: several waiters of one or several classes ending in any order, the owner raising or lowering its own class during a lend, an end that comes twice (the handle carries a table-wide 16-bit generation, so a stale end misses even after its slot was taken again by any thread, until 65,536 later lends wrap the counter), a lend the limit refuses while the owner changes its own class (the refused class stops counting, the owner's class is applied and reported), a thread leaving with lends in flight (`hle_thread.c`'s `thread_exit` drops its entry; a thread that dies any other way leaves it until its lends end, and a new thread given that tid meanwhile has its class folded in as the base), more than 32 waiters of one class on one owner (counted past the slots; only such a lend's end is not instance-checked), 257 owners at once (the table holds 256; the 257th lends nothing and says so once), a class the limit refuses (not reported by `dm_qos_self`, since the port keeps the class the kernel accepted); a nice below `RLIMIT_NICE` (its value for an app process is not measured yet) fails with EACCES, said once, and that waiter waits without the lend. `port.h` is now the only file in `dm/host`, `dm/gfx/nvn` and their tests that spells CommonCrypto, `clonefile` and the pthread QoS calls (the audit's `commoncrypto` and `qos-class` patterns now also catch the streaming `CC_SHA256_*` names and `pthread_override_*`, which they missed), recorded as 22 rows of one file in place of 51 spread over ten: 845 to 816 hits under the widened patterns (`apple-api` 392 to 363). Mach time is still spelled where it is not a clock reading: the NVN profiling ticks that `nvn_entry.S` takes from `mach_absolute_time` in assembly and converts in `hle_nvn.c`, and `task_power_info` and the time-constraint policy there, which belong to the Mach task-info and thread-policy groups. Open beside the clone: `hle_fs.c`'s case-collision names are an xattr named `org.d2rmobile.guest-name`, read and written with Apple's six-argument `getxattr` / `setxattr` / `removexattr` (`XATTR_NOFOLLOW`, `ENOATTR`); Linux takes four arguments (`lgetxattr` for no-follow, `ENODATA`), rejects a name outside its namespaces, and `user.*` is the one an app may set and the only one compat's clone copies, so the port uses a `user.*` name (`dm_xattr_*` in `port_android.c`; `hle_fs.c` compiles on bionic). `dm/android/CMakeLists.txt` lists `port_android.c` in `ANDROID_SRCS`, and it is built for arm64 with NDK r29 and run on the device (HANDOFF §8 item 9); on OHOS/musl `pthread_gettid_np`, which `port_android.c` and compat's `mach.h` use for the thread id, does not exist. The second step put the rest of the Apple API list behind the same header (HANDOFF §8 item 4): the table sections and `HLE_FORCE_BIG`'s assembly spellings (`DM_SECTION`, `DM_ASM_*`, `dm_section`), the signal context (`dm_uc_ss`, `dm_uc_ns`), mappings (`dm_vm_region`; `dm_guest_as_reserve` backs the guest address space with a memfd and `MAP_SHARED`, and `dm_vm_alias` duplicates physical mappings for virtual pools and write-watch aliases on Linux/Android), the time-constraint policy and the task power facts (not available on bionic, said once), the process start time, performance levels, a heap of its own, extended attributes, descriptor paths, a timed condition wait, thread names, a semaphore, a deferred call and the SIGTERM hand-off; `AudioToolbox` and `VideoToolbox` / `CoreMedia` / `CoreVideo` / `CoreFoundation` have real backends for the two that matter to a running game (`dm/android/apple_stubs.c`): the `AudioUnit` output plays through AAudio, and VideoToolbox's H.264 decoder decodes through `AMediaCodec` into an NV12 `CVPixelBufferRef`. AAC through `AudioConverter` is still an interface stub that says so once with `[RED]`, so an AAC track is silent. It is compiled for arm64 with NDK r29 and runs on the device (HANDOFF §8 item 9).

Two things the audit does not itemise, because the unit is the file: the Apple types inside a `.m` file (an Objective-C implementation file is Apple-only as a whole; `nvn_mtl.m` alone would add thousands of `MTL*` lines that say nothing new) and the `_`-decorated symbols of a `.S` file (`entry.S`, `nvn_entry.S` and `nvn_thunks.S` are Mach-O assembly throughout, so assembling them for ELF is a whole-file change). `dm/tools/tests/test_android_audit.py` drives every category, the normalisation, the exclusion list and both kinds of failure on a synthetic tree.

### The device page is 4 KiB and `nvn_dirty.c` already follows it

`dm/gfx/nvn/nvn_dirty.c` tracks coherence per page, so the page size decides whether it is correct on a 4 KiB device. It takes the page from `getpagesize()` (`:128`), rounds every pool to it (`:148`), and protects, unprotects and stamps in units of it (`:77`, `:107`, `:182`, `:202`), so it needs no change: on the Galaxy S23 Ultra a pool simply spans four times as many pages. The two 16 KiB mentions in that file are comments that no longer describe the code — `:27` ("ranges are rounded to host pages (16 KB)") and `:99` ("one system call per 16 KB page", whose measured call count is a quarter of what 4 KiB pages cost). The other `0x4000` sites are not host-page assumptions: `dm/host/loader.c:212` and `:214` are the rewriter's 16 KiB key page (a guest on-disk format), `dm/host/hle_svc.c:574` and `dm/gfx/nvn/nvn_mtl.m:1740` round to `getpagesize()` and only say 16 KB in the comment.

One site does depend on it: `dm/host/probe.c:168`-`:171` aligns the probe instruction down to 16 KiB and calls `mprotect` on 0x4000 bytes. That protects up to three pages the probe does not own, and fails (`ENOMEM`, then `die("probe mprotect")`) when one of them is not mapped — inferred from the code, not seen failing. The safe form is the one the watch path already uses at `:355`: `uint64_t pg = at & ~(uint64_t)(getpagesize() - 1); mprotect((void *)pg, getpagesize(), prot)`.

## The app's graphics defaults

### Every `DM_GFX_*` switch the engine documents for Android was unset

- **Symptom:** on the S23 Ultra a course runs at 12–19 fps with the GPU at 19.5 ms a frame, and the render thread reports `submit_cpu_ms=58` with `parts_ms_per_frame image=13.4`. The engine's own log lines say `texture checks through the dirty tracker=0`, `vertex/index cross-frame cache=0 tracker=1`, `pipeline memo=0`, `defer events=0` and `native BC textures=0`.
- **Cause:** `dm/gfx/vulkan/engine/xbg_game.cpp` documents a set of switches as "the Android app sets …" (the texture dirty check, the vertex/index cache, the pipeline memo, the async command-pool reset, the frame-timing sample, native BC, deferred events, writeback skipping, shader reuse, the upload prologue, the cross-view guard, the two translator clean-ups, the two shader rewrites) and `dm/android/jni_android.c` set none of them. Every one ran at its desktop default, so a bound texture was re-hashed on its 4th and then every 16th submission (the `image` scope above, and the largest single CPU item of the frame), the vertex and index ranges were copied again every frame, and pipeline lookups serialised the create info on every draw. The two rewrites that the 64-lane subgroup of an Adreno needs for correct warp-aggregated shaders were off as well.
- **Fix:** `nativeStartHost` sets them before the host thread starts, one `setenv(…, 0)` per switch so an existing value wins and a profile or a shell export can still override it, and logs each with the value in effect (`nativeStartHost: DM_GFX_TEX_DIRTY=1 (hash a bound texture only after a guest write to its pages)`). A `gfx-*` marker file in the shader directory's parent still takes precedence over the environment. The values are the ones the engine names: `TEX_DIRTY=1`, `VCACHE=1`, `PIPE_MEMO=1`, `ASYNC_POOL_RESET=1`, `PERF_SAMPLE=0`, `NATIVE_BC=1`, `DEFER_EVENTS=2`, `WB_SKIP=1`, `SHADER_REUSE=1`, `UPLOAD_PROLOGUE=1`, `XVIEW_GUARD=1`, `LDC_FOLD=1`, `FORWARD_TEMPS=1`, `QUAD_DERIVATIVES=1`, `WARP32=1`.
- **Found on:** the S23 Ultra's own `NVN PERF` lines (§Status of `HANDOFF.md`). Not measured after the change yet: it needs a new build on the device.

### The present blit decoded an sRGB swapchain texture a second time

- **Symptom:** the whole picture darker and more saturated than on the Switch, every channel at every level equal to the Switch value decoded from sRGB once more, and 8-bit banding in the gradients; the 2D UI keeps its flat colours, so it reads as a 3D-only fault.
- **Cause:** `vkCmdBlitImage` converts an sRGB source image to linear and converts back only when the destination is also sRGB. `dm/android/vulkan_present.cpp` always took the surface's UNORM format (`R8G8B8A8_UNORM` / `B8G8R8A8_UNORM`), so a game whose swapchain texture is `RGBA8_SRGB` or `BGRA8_SRGB` had its stored bytes decoded once on the way to the screen. The Switch scans out the stored bytes, and `nvn_mtl.m` does the same by sampling such a texture through a non-sRGB view (`present_raw_src`).
- **Fix:** the swapchain now takes the encoding of the presented image. `present()` records `is_srgb(source_format)` in `want_srgb` and asks for one rebuild when it changes; `create_swap()` picks the 8-bit RGBA/BGRA surface format of that encoding, skipping any format without `VK_FORMAT_FEATURE_BLIT_DST_BIT`, and falls back to the other encoding (decoding once, as before) when the device offers only that one, so no device loses presentation. A blit between two formats of the same encoding converts neither way. The `Swapchain:` log line now carries `format=`, `srgb=` and `source_srgb=`.
- **Found on:** read from `nvn_mtl.m`'s present step against `vulkan_present.cpp`; not observed on a device yet, and `0100152000022000`'s swapchain format is not recorded, so the new log line is what will say whether it fires.

## Adreno driver gates

### The Adreno 740–799 family loses the device on the quad-derivative and warp32 rewrites

- **Symptom:** on a Snapdragon 8 Gen 2 or 8 Gen 3 phone the app dies about two seconds into the boot, before the main menu: dmesg shows `gpu timeout ... status 00EF1087` (a kgsl GPU page fault) and the next submit returns `VK_ERROR_DEVICE_LOST` (-4).
- **Cause:** the SPIR-V of two shader rewrites written for Adreno 730 (`xbg_spirv_quad`, `xbg_spirv_warp`) is accepted but faults in the Adreno 740–799 driver; both run on 730 and 830. See [upstream issue #141](https://github.com/jhaizhou-ops/d2r-mobile/issues/141).
- **Fix:** `xbg_adreno_policy.h` reads the model from the Vulkan device name (`Adreno (TM) 740` → 740; anything that is not three digits is unrecognized) and, for vendor `0x5143` and model 740–799, defaults both rewrites off; a marker file (`gfx-quad-derivatives`, `gfx-warp32`) still turns either on explicitly. The precedence is marker file, then device family, then `DM_GFX_QUAD_DERIVATIVES` / `DM_GFX_WARP32`: the device check must come first because the Android JNI sets both environment variables to 1 on every phone. The log line is `NVN Adreno 740/750 (device "..."): the quad-derivative and warp32 rewrites default off; a marker file still turns either on`.
- **Found on:** upstream's reports, not reproduced here. The target device (Galaxy S23 Ultra, Adreno 740) is in this family, so the gates apply to it by default.

### Adreno 750–799 segfaults while building a pipeline from a subgroup helper

- **Symptom:** pipeline creation crashes inside Qualcomm's `libllvm-qgl.so` at address `0x48` for shaders whose subgroup instructions sit in a called helper function, on Samsung and Xiaomi Snapdragon 8 Gen 3 phones.
- **Cause:** a driver compiler defect in the Adreno 750–799 family ([upstream issues #123](https://github.com/jhaizhou-ops/d2r-mobile/issues/123), [#153](https://github.com/jhaizhou-ops/d2r-mobile/issues/153), [#166](https://github.com/jhaizhou-ops/d2r-mobile/issues/166)).
- **Fix:** when the engine loads such a shader it inlines the helpers into the entry point (the import pack is unchanged). The marker file `gfx-inline` forces it on or off; on this family it defaults on, and it is only compiled when `XBG_HAVE_SPIRV_OPT` is defined. Without SPIRV-Tools the code logs `NVN helper inlining is not built into this package; shaders load as they are` and turns the workaround off — so a build that drops SPIRV-Tools also drops the only mitigation for these phones.
- **Found on:** upstream's reports; not reproduced here. The Adreno 740 is outside this family but is in the 740–799 rewrite-gate family above, so the two gates do not overlap on our target.

## The ABI and host gaps

### The vendored replay does not link against this repository's `nvn_mtl.h`

- **Symptom:** linking `dm/gfx/vulkan/nvn_vk.c` into the host would report undefined references for 27 entry points this repository declares, and the objects the replay layer expects are not the ones this repository lays out.
- **Cause:** the two `nvn_mtl.h` headers diverged in both directions after the fork point. This repository declares 27 entry points that upstream's `nvn_vk.c` does not define: 12 of the 29 `nvn_mtl.h` declares (`mtl_alias_drop_pool`, `mtl_device`, `mtl_device_classic`, `mtl_ext_tex`, `mtl_present_ext`, `mtl_queue_activate`, `mtl_queue_forget`, `mtl_set_depth_zero`, `mtl_set_origin_lower_left`, `mtl_set_queue_origin_lower_left`, `mtl_wait_acq`, `mtl_vbuf_stats`) and 15 that only `nvn_obj.h` declares (`mtl_ab_gpu`, `mtl_cpu_tex_count`, `mtl_link_rate`, `mtl_link_stalled`, `mtl_link_tick`, `mtl_link_wait_ticks`, `mtl_pkg_edge_skips`, `mtl_present_test_stall`, `mtl_reg_image`, `mtl_snap_acquire_wait`, `mtl_snap_on`, `mtl_sub_fill`, `mtl_tex_cpu_written`, `mtl_tex_gpu_owned`, `mtl_tex_init`). `mtl_present_wait`, counted as a 13th before this was measured, is in fact defined by the adapter (`nvn_vk.c:83`). In the other direction `nvn_vk.c` defines 12 `mtl_*` functions neither header declares, two of them D2R-specific (`mtl_ui_ghost`, `mtl_ui_ghost_rect`): inert for linking, but they show the two sides were written against different headers. ### The replay refused a record of more than one viewport

- **Symptom:** the engine's fatal `Multiple viewports unsupported` (earlier `Invalid viewport record`) at the first `SetViewports` with `n > 1` or `first != 0`; before any draw, a shader that selects a viewport died at load with `FATAL: Shader stage 3 has unhandled capability 57` (`MultiViewport`; 70 / 5254 for a vertex or tessellation stage, 5255 for a viewport mask) or `declares extension requiring explicit backend support` (`SPV_EXT_shader_viewport_index_layer`). The game itself reads the host's device table for `NVN_DEVICE_INFO_MAX_VIEWPORTS` (`hle_nvn.c` `g_devinfo[0x26] = 16`), so it believes it has 16 viewports whatever the engine draws. Payload `P6` in `opcode_map.txt`.
- **Cause:** the vendored engine kept one `VkViewport`, declared one dynamic viewport in every pipeline, set one at every draw and refused every viewport capability in `validate_capabilities`. NVN keeps 16: `SetViewports(first, n)` writes a subrange of the array, the last pre-raster stage (vertex, tessellation evaluation or geometry) picks one per primitive by writing `gl_ViewportIndex` (or fans a primitive out to several with `gl_ViewportMask`, `NV_viewport_array2`), and a shader that writes neither rasterizes into viewport 0. The Metal replay binds viewport 0 only ([Geometry reader viewport masks](shaders.md#geometry-reader-viewport-masks)); Vulkan can do better, since `multiViewport` pipelines take up to `maxViewports` viewports as dynamic state.
- **Fix (in the draw; not reachable end to end yet, see the open items):** `OP_VIEWPORTS` writes `viewport[first..first+n)` and keeps `viewport_n`, the array's length (the highest index set plus one; the range check is `first <= 16 - n`, no signed sum, in `OP_VP_SWIZZLE` too). `XbgRasterFacts` gained `viewport_index` / `viewport_mask` (an Output decorated `BuiltIn ViewportIndex` / `ViewportMaskNV` in a vertex, tessellation-evaluation or geometry module). `draw_viewports()` is the count a draw declares: `viewport_n` when the bound geometry, tessellation-evaluation or vertex shader selects a viewport, 1 otherwise. The pipeline's `viewportCount = scissorCount` is that count (it is in `xbg_graphics_pipeline_key` and now explicitly in `PipeMemoKey.viewports`: `viewport_n` **is** a pipeline input, which reverses the earlier note); the draw builds that many `VkViewport`s with `xbg_nvn_viewport` (the one recorded depth range for each, since `hle_nvn.c` records `SetDepthRanges` / `SetScissors` index 0 only; an index above 0 the game zeroed or never set is a 1x1 viewport behind an empty scissor, NVN's empty viewport, since Vulkan wants a positive size), applies each viewport's swizzle (`OP_VP_SWIZZLE`: `NEGATIVE_Y` is the viewport flipped about its centre, as `nvn_mtl.m` does; any other swizzle is one `[RED]` line and drawn unswizzled), checks the device bounds, and sets them and the one scissor replicated with `vkCmdSetViewport` / `vkCmdSetScissor(0, count)` through the bind cache (`vpn` / `scn`). `validate_capabilities` accepts `MultiViewport` (57) under `multiViewport`, `ShaderViewportIndex` (70), `ShaderViewportIndexLayerEXT` (5254) and the `SPV_EXT_shader_viewport_index_layer` extension under the **enabled** `shaderOutputViewportIndex`, and refuses `ShaderViewportMaskNV` (5255) and `SPV_NV_viewport_array2` with a `[RED]` line and the reason (the capability numbers are the SPIR-V unified registry's; the tree has no `spirv.h` to include, so they are checked against the file's existing numbering and `BuiltIn ViewportMaskNV = 5253`, not against a header). A draw that selects needs `multiViewport` (`cfg.enabled_core`) with `count <= maxViewports`, and, when the writer is a vertex or tessellation stage, `shaderOutputViewportIndex` **enabled at device creation**: the engine cannot see that from `cfg`, so `xbg_game_set_viewport_features(shader_output_viewport_index, multiview)` (the shape of the mirror-clamp setter, default false) is what the host reports, checked against the physical device's support (`VkPhysicalDeviceVulkan12Features`, or `VK_EXT_shader_viewport_index_layer` below 1.2, logged at initialization as `NVN viewports maxViewports=… multiViewport=… shaderOutputViewportIndex=… multiview=… (supported …)`). `nvn_cover`'s one-viewport proof keeps holding for every non-selecting draw (and is skipped for a swizzled viewport 0, whose flip the proof is not told about). **Open, and why the path is not reachable yet:** (1) `dm/android/vulkan_present.cpp` now asks the loader for 1.2 (`vkEnumerateInstanceVersion`; 1.1 on an older loader), queries `VkPhysicalDeviceMultiviewFeatures` and, on a 1.2 device under a 1.2 instance, `VkPhysicalDeviceVulkan12Features`, and chains into `vkCreateDevice` only what the device has: `shaderOutputViewportIndex` + `shaderOutputLayer` (else the `VK_EXT_shader_viewport_index_layer` extension when listed; with the 1.2 struct in the chain, `samplerMirrorClampToEdge` is stated in it too whenever the mirror-clamp extension is enabled, as VUID-VkDeviceCreateInfo-ppEnabledExtensionNames-02832 requires, quoted from memory: no registry copy in the tree) and `multiview`; the engine's "supported" takes the same two routes (the 1.2 features on a 1.2 device, else the extension), and `nvn_vk.c` treats the setter's -2 as a `[RED]` line, not a failed initialization, since only a viewport-selecting shader needs the feature; `dm_vk_config.shader_output_viewport_index` / `.multiview` carry the result and `nvn_vk.c` calls `xbg_game_set_viewport_features` with them right after the mirror-clamp setter, before any shader load (one log line: `Vulkan instance 1.2 device 1.3: shaderOutputViewportIndex=1 (Vulkan12Features) multiview=1 multiViewport=1` is the expected shape on the S23 Ultra). **Unmeasured:** `vulkan_present.cpp` passes `g++ -fsyntax-only` with Android header shims and nothing more ran; ### The Vulkan replay ignored the window origin, the depth mode and the restart index

- **Symptom:** a game that keeps NVN's lower-left window origin (Link's Awakening, Absolum, the GL layer's games: [Lower-left window origin](rendering.md#lower-left-window-origin)) would come out upside down with its facing reversed on the Vulkan replay, and `mtl_set_origin_lower_left`, `mtl_set_queue_origin_lower_left` and `mtl_set_depth_zero` in `nvn_vk.c` did nothing (`(void)on`); a strip draw whose game set a restart index other than all-ones (`SetPrimitiveRestart(1, index)`) would not restart on it, an 8-bit index stream with restart would lose it when widened to 16 bits (`0xff` becoming `0x00ff`, the case `nvn_mtl.m` warns about once), and a list draw with restart on would be a Vulkan validation error (`primitiveRestartEnable` on a list topology without `VK_EXT_primitive_topology_list_restart`); `OP_RENDER_COND` read its two counters without resolving the GPU work pending over them, and then treated every pending report as unknown, so a conditional clear after a timestamp report was drawn where `nvn_mtl.m` skips it; the first `ReportCounter(TIMESTAMP_TOP)` (0x10, which Tears of the Kingdom issues after each conditional clear) or report of a pipeline statistic ended the replay at `need(type==TIMESTAMP || type==SAMPLES_PASSED, "Unsupported pipeline statistics query")`, and a `ResetCounter` of any type but samples passed at `"Unsupported pipeline counter reset"`; `OP_BIND_VATTR` was listed as needing `first > 0`.
- **Cause:** the fork's engine has no window-origin or depth-mode state (its one title set the upper-left origin and the near = 0 depth mode at start, as most games do), its restart came straight from the record, and the render-condition handler ported in the second sprint read guest memory directly. The vertex-attribute note was wrong: NVN's `BindVertexAttribState(n, states)` has no `first`, the writer records 0 (`hle_nvn.c`), and the Metal replay also replaces the table from 0.
- **Fix:** `xbg_game_set_window_origin(lower_left)` and `xbg_game_set_queue_origin(lower_left)` (separate engine entry points; `nvn_vk.c`'s setters call them independently to avoid a race where setting device origin re-sent a stale queue origin) keep the two origins as atomics: `xbg_submit` captures both per submission into `sub_origin` (`device_ll`, `queue_ll`), so `draw()` reads them consistently under the engine mutex without interference from concurrent submits. With the device origin lower-left every viewport is flipped about its centre at the draw (`sub_origin.device_ll`, the same flip `nvn_mtl.m` applies, composing with the `NEGATIVE_Y` swizzle flip), and the window image is stored bottom-up, so `vulkan_present.cpp` flips its blit (`dm_vk_present_flip`, swapping the source y offsets) as the Metal present does; the queue's captured raster origin decides `rs.frontFace` (`front == CCW` XOR `sub_origin.queue_ll`, `nvn_mtl.m`'s rule, [Queue initialization captures the raster origin](rendering.md#queue-initialization-captures-the-raster-origin)) and is in `PipeMemoKey.origin`; `nvn_cover`'s proof keeps the load under either origin (it is not told about the flips). The depth mode has no engine counterpart: the Metal replay picks a vertex entry point that converts near = -w to near = 0 (`entry_z`), the Vulkan bundles have one entry point, so a game that keeps the GL mode gets `[RED] NVN depth mode near=-w (GL) kept by the game: … not implemented` once, at the first submission (the host sets the default at device creation and the game changes it before drawing), and its depth is mapped as near = 0: open, it needs a depth-range conversion in the shader chain or the vertex shader. Restart: `primitiveRestartEnable` is declared only for the strip and fan topologies (3, 5, 6, 11, 13), off for lists and patches (a list draw whose indices held the restart value would differ, not expected: a list has no primitive to end early); when restart applies and the game's index, as the stream's width sees it (`index & all_ones`: `0xffffffff` on a 16-bit stream is `0xffff`, the common case, which keeps the snapshot path), is not Vulkan's fixed all-ones, the indices are copied with that value mapped onto all-ones (an 8-bit stream is widened anyway, its restart value `index & 0xff` going to `0xffff`), after `cpu_access` on the guest range; the residual difference is a real index equal to all-ones in such a stream, which would restart. **Unverified:** that the Switch GPU compares the restart index at the stream's width (so `0xffffffff` restarts an 8-bit or 16-bit stream) is an assumption, not a measurement: it is the masking `nvn_geometry.inc` applies (`S.restart.index & (size == 1 ? 255u : size == 2 ? 65535u : UINT32_MAX)`), while `nvn_primitive.h`'s fan and quad expansion compares the unmasked index and `nvn_mtl.m`'s 8-bit strips do not restart at all (its one-time log line), and nothing in the tree records what the hardware does. `OP_RENDER_COND` decides each of the two 64-bit counter fields (at the record's address and 16 bytes on) without touching the GPU, from `pending_reports` / `pending_writebacks` (the overlap test `cpu_access` uses): when the last report still pending over a field is a timestamp report (`TIMESTAMP` or `TIMESTAMP_TOP`) at exactly that address, the field is known 0, the counter a timestamp report writes, as `nvn_mtl.m`'s `rc_value` counts a timestamp report replayed earlier in the same submission (Tears of the Kingdom's conditional clears: the first clear of a target reports into the record and later conditional clears of that target are skipped; drawing them is the black 3D scene `nvn_mtl.m` describes); any other pending report over the field (samples passed, a pipeline statistic, a report at another address that reaches it) or a pending writeback leaves it unknown and keeps the draws, as `rc_value`'s "unknown, drawn"; a field nothing is pending over is read from memory. Parity with `rc_value` holds for those cases only: `nvn_mtl.m` also keeps an address that a non-timestamp report ever wrote unknown for good (`rc_occ`), where the Vulkan replay reads the settled value once the report is written, so a condition on a settled occlusion result can skip draws here that the Mac draws. Resolving the pending work instead (a first version called `cpu_access`, which ends in `resolve_pending()`) would have been a full GPU wait in the middle of the replay, for a conditional the game reads one frame late anyway. Counters: `TIMESTAMP_TOP` is a top-of-pipe `vkCmdWriteTimestamp` (no wait for the earlier work; `nvn_mtl.m` takes its segment's GPU start) with counter 0, like `TIMESTAMP` at the bottom of the pipe; a pipeline statistic (2..0xf, or any other type) is written as counter 0 with the bottom-of-pipe time and one `[RED]` line, and its `ResetCounter` is ignored with one `[RED]` line (a timestamp reset silently), as `nvn_mtl.m` neither implements nor stops on them. A timestamp report's counter field (`NVNcounterData.counter`, the first 8 bytes) is always 0 on the Vulkan replay (`write_report`), on purpose: that is what the GPU writes, by `nvn_mtl.m`'s own account (its comment at `:610`, the reason the render-condition skip works on the Mac), and the known 0 above depends on it. `nvn_mtl.m` writes 0 there only under `render_cond`; without it, `post_run` (`:1439`) puts the time into both fields, a host convention and not the hardware's. The time is in the second field (`NVNcounterData.timestamp`, 614.4 MHz ticks), which is what `nvnDeviceGetTimestampInNanoseconds` reads (`hle_nvn.c`), so a game that converts through that call or reads the second field sees the same times on both replays. A game that polls the first field of a timestamp report sees 0 on Vulkan: a wait for it to become non-zero would never end, and a time difference taken from it would be 0. On the Mac without `render_cond` it would see the time. If the hardware writes 0 there, as `nvn_mtl.m` says, such a game would fail on the Switch too, so none is expected; that claim has not been checked on a Switch. The `OP_BIND_VATTR` note in `opcode_map.txt` now says what the record is.
- **Found on:** QA's reading of the engine against `nvn_mtl.m` (rounds B–F), not on a game: no Vulkan draw has run, so the flips, the winding and the restart mapping are checked by `g++ -fsyntax-only` and by reading, and wait for the host bring-up; a lower-left-origin game is the first to look at then.

### The guest thread slots assumed Darwin's TSD layout

- **Symptom:** inferred from the code, not seen on a device: the Android host dies with SIGSEGV at the first module load, in `loader.c`'s `tsd_check` (a load from address `0 + 8 × key`), and with that check gone the first rewritten site the game runs (an x18 access, an `mrs tpidr_el0` / `tpidrro_el0`, an `svc`) faults the same way. Since the fix, a module rewritten for the other platform stops the loader with `<module>.fixups.tsv: rewritten for Apple (KSLOT_TP_OFF 0), this host is Android: rewrite the modules with dm/tools/patch_nso.py --target=android`, and another component holding bionic's app slot stops the first guest thread with `[RED] guest thread slots: bionic's TLS_SLOT_APP of thread … holds …, not this host's table`.
- **Cause:** the rewriter (`dm/tools/patch_nso.py`) keeps the guest's x18, `tpidr_el0` and `tpidrro_el0` and the host gate's address in four thread slots (K18, KTLS, KTLR, KGATE, `dm/host/dm.h`) and reaches one as `mrs tpidrro_el0`, plus the key page's `key × 8`, then a load or store. On Darwin TPIDRRO_EL0 is the pthread TSD array, so that word is the value of pthread key `key`: the host writes the slots with `pthread_setspecific` (`thread.c`, `loader.c`), reads x18 with `pthread_getspecific` (`hle_thread.c`'s SVC entry and pause signal) and proves the layout once by dereferencing TPIDRRO_EL0 (`tsd_check`). An AArch64 Linux task reads TPIDRRO_EL0 as 0 (the kernel keeps it for 32-bit tasks and zeroes it, or uses it as a KPTI scratch register, for 64-bit ones), and bionic's thread pointer is TPIDR_EL0, whose words are bionic's thread control block; pthread key values live in a separate `bionic_tls` block, not at `pointer + 8 × key` from either register. Nothing in the tree said so: no gate, no audit pattern, no entry.
- **Fix:** a target switch in the rewriter and one slot interface in the host. `patch_nso.py --target=android` emits `mrs xN, tpidr_el0; ldr xN, [xN, #16]` where the Apple code has `mrs xN, tpidrro_el0` (`emit_thread_base`, the one place a thread register is read; the key page, its `key × 8` and the slot access after it are unchanged) and writes `# KSLOT_TP_OFF 0x10` into `fixups.tsv`; `--target=apple`, the default, writes the patched image, gates, sites and fixups byte for byte as before (`build_src.sha256` holds the rewriter's own hash, so `build_ipa_from_nsp.py` re-runs it once; the 13 call sites only go through the helper; checked by diffing the rewriter against HEAD with the helper spelled back, and pinned by the Darwin word sequence in `test_thread_slots.py`), and an Android output's `build_src.sha256` names its target. Word 2 of bionic's thread control block, `TLS_SLOT_APP` (`libc/platform/bionic/tls_defines.h`, quoted from memory: the tree has no bionic source), is the one bionic leaves to the app from Android 10, API 29; it held `errno` before, so `dm/android/CMakeLists.txt` now requires `ANDROID_PLATFORM >= 29`. The other words are the dynamic linker's DTV, the thread id, the GL / GLES loader's two (`TLS_SLOT_OPENGL`, `TLS_SLOT_OPENGL_API`), the stack guard, the sanitizers' (`TLS_SLOT_SANITIZER`, HWASan) and ART's thread (`TLS_SLOT_ART_THREAD_SELF`), and the slots below the block are bionic's own, the native bridge's and MTE's: so neither the Vulkan or GL loader, the vendor driver through them, nor a sanitizer writes word 2; a third-party library in the app could (Go's runtime is one: with cgo on android/arm64 it keeps its `g` in `TLS_SLOT_APP` from API 29, golang/go#29674, as QA reported it; not checked here), and `dm_kslot_set` refuses a word it did not write (fatal with the `[RED]` line above: either owner breaks the other). `dm_kslot_new` also asks the device (`android_get_device_api_level()`): below 29 it refuses with a `[RED]` line, since the build's floor says what the NDK may call and not what the phone runs, and word 2 is `errno` there. On a thread whose table was never set (no `guest_thread_init`), rewritten code loads its slot from `0 + key × 8`; `crash.c` names that fault (address 8..0x27, pc in a module, no KGATE slot) with a `[RED]` line on bionic. The host reaches the slots only through `dm/host/port.h`'s `dm_kslot_new` / `dm_kslot_get` / `dm_kslot_set`: inline `pthread_key_create` / `pthread_getspecific` / `pthread_setspecific` on Apple, the calls it made before; on bionic (`dm/android/port_android.c`) a five-word table per thread in ELF TLS (`static __thread`, native in bionic from API 29), word 0 a tag and words 1..4 the slots under key numbers 1..4 (so a key page entry is 8..32 and the loader's "entry is 0" check still holds), put in word 2 by the thread's first `dm_kslot_set`; `dm_kslot_get` reads the thread control block and never the TLS variable, so it stays async-signal-safe for the pause signal. `loader.c` refuses a module whose `KSLOT_TP_OFF` is not this host's (`DM_KSLOT_TP_OFF`: 0 on Apple, 16 on bionic), and `tsd_check` is per platform: Apple's body is unchanged, bionic's writes a slot and reads it back with the instructions the rewriter emits (`dm_kslot_guest_read`). The guest's own `msr tpidr_el0` stays rewritten into KTLS on both targets, so the guest never writes the TPIDR_EL0 bionic runs on; x18 stays rewritten too (on Android it is the shadow call stack register of bionic and the system libraries). `android_audit.py` gained the `thread-register` pattern (an `mrs` of `tpidrro_el0` / `tpidr_el0` in the host's code), whose one hit today is Apple's `tsd_check`.
- **Found on:** reading the rewriter and the host for the Android port, before any device run (HANDOFF §8). Checked: `dm/tools/tests/test_thread_slots.py` runs the 13 stubs that reach a slot (`site_plain`, `site_sp`, `site_cond`, `site_pcrel`, `site_br`, `site_br_tab`, `site_blr`, `site_br_call`, `site_sysreg_read`, `site_tpidr_write`, the gate's `emit_gate_call`, `site_window`, `site_retry_window`) for both targets on a small AArch64 interpreter that models each platform's thread registers and refuses the register a target must not read; capstone's decoding and the x18 substitution are given by hand, not computed, so the instructions are hand-made ones, not a game's. A structural check over the rewriter's source requires every `emit_slot_addr(reg, ...)` to follow an `emit_thread_base(reg)` in the same function and no other function to spell a thread-register read, and evaluates the Android `KSLOT_TP_OFF` fixups line against `port.h` and `loader.c`; both word sequences are pinned (`mrs x3, tpidr_el0` = `0xd53bd043`, `ldr x3, [x3, #16]` = `0xf9400863`). Every mutation QA listed fails it (in scratch copies): the raw Darwin word in `site_window`, `site_retry_window`, `site_cond`, `site_br_tab`, `site_pcrel` or `site_sp`, the wrong register to `emit_thread_base` in `site_window`, the `KSLOT_TP_OFF` line dropped, its value or its key changed, the table load removed, `tpidrro_el0` on Android, word 3. Open, unverified without the NDK and the device: that a new thread's word 2 is 0 (assumed: bionic zeroes the control block with the thread's static TLS), that nothing in the app process writes it, the inline assembly of `dm_kslot_guest_read` (only `gcc -fsyntax-only` on x86 has seen it), and the packing step: no Android packing path runs the rewriter yet, and it must pass `--target=android` (the loader refuses the default's output).

### A guest polling an event read a stale value on the Vulkan replay

- **Symptom:** inferred from the code, not seen on a device: a game that waits for a GPU event by polling `nvnEventGetValue` with no further submit spins on the old value (a hang or a lost frame), and a CPU `nvnEventSignal` issued while a GPU write to the same event is still pending is later overwritten by that older write. `dm/gfx/vulkan/engine/tests/event_order_test.py` failed (at HEAD too) on its source gate: `hle_nvn.c` never called `mtl_event_read`.
- **Cause:** the Vulkan engine defers an `OP_SIGNAL_EVENT` write in `pending_events` and publishes it when its slot retires, and offers `xbg_game_event_read` (through `nvn_vk.c`'s `mtl_event_read`), which drains the graphics worker and, if a pending write targets that address, completes the GPU work first. Nothing called it: `hle_nvn.c`'s event functions read and wrote the storage directly, which is right for the Metal replay (it writes the value at the command buffer's completion, `mtl_sub_event`) and not for a replay that holds writes back. `abi_gaps.py` listed `mtl_event_read` among the adapter's undeclared extras, which hid the missing caller.
- **Fix:** `mtl_event_read(const volatile uint32_t *val)` is declared in `dm/gfx/nvn/nvn_mtl.h` with its contract, and `hle_nvn.c` calls it before every CPU access to an event's storage: `nvnEventInitialize` (storage taken over), `nvnEventFinalize` (storage given back), `nvnEventGetValue` and the read-modify-write of `ev_signal` (`nvnEventSignal`). The Metal build gets a weak no-op default beside the callers (the pattern of `dm_vk_drain`), so neither platform needs a preprocessor branch; `nvn_vk.c`'s strong definition replaces it on Android. `abi_gaps.py`'s extra count went from 29 to 28.
- **Found on:** QA's round H reading of the event path and `event_order_test.py`, which passes now; no Vulkan draw has run.

### `xbg_game.cpp` compiled as C++ fails on `nvn_obj.h`'s helpers and on the fork's opcode

- **Symptom:** the Android toolchain, clang, reported 10 errors on `xbg_game.cpp`: `cannot initialize return object of type 'const p_bind_vbuf *' with an lvalue of type 'const void *'` at `dm/gfx/nvn/nvn_obj.h:130`, then `:131`, `:138`, `:139`, `:151`, `:152`, `:167` and `:168`, and `use of undeclared identifier 'OP_COPY_IMAGE_STRIDE'` at `xbg_game.cpp:3812`. ## The desktop smoke build

`dm/gfx/vk/engine_smoke/` builds the engine alone on Linux x86_64 — system Vulkan headers, GCC 15.2 or clang, Mesa lavapipe or the machine's GPU — links it to a 60-line harness that creates the instance, device and queue `xbg_game_config` asks for, and prints the per-translation-unit state plus the `mtl_*` gap above. The engine sources are compiled in place; the one local edit they now carry (`xbg_game.cpp`'s compatibility block) is recorded in the manifest, so it stays green. Its [README](../../dm/gfx/vk/engine_smoke/README.md) carries the commands and every measured line; what it established:

- All 8 C files and all 12 C++ files compile with `-Wall -Wextra`, under gcc 15.2 / g++ and clang 21.1.8 / clang++, with no workaround and no `-fpermissive` (`xbg_texture.c` needs `-D_GNU_SOURCE` on glibc, which declares `pthread_setname_np` only under `__USE_GNU`; bionic declares it unconditionally). `dm/gfx/nvn/nvn_obj.h` and `nvn_mtl.h` also compile alone as C and as C++ with `-Werror`.
- `build/engine_smoke` prints `xbg_game_initialize -> 0` and `xbg_game_shutdown -> 0` and exits 0 on Mesa 26.0.8 lavapipe (`llvmpipe`, api 1.4.335) and on an RTX 5060 Ti (api 1.4.312), with 60 and 63 engine log lines and no fatals.
- Initialization needs neither guest memory nor a shader bundle. Its only inputs are a non-NULL physical device, device and queue, a `shader_directory` string, a non-zero fence timeout (`xbg_game.cpp:3886`), a queue family with `GRAPHICS` and `COMPUTE` (`:3906`) and the features `enabled_core` asks for (`:3905`). A bundle is read lazily at the first program bind, and `load_shader` then fails loudly (`xbg_game.cpp:1980`, `Missing genuine shader bundle %s`, then the length, header and exact-extent checks at `:1981`–`:1983`) on a `<shader_directory>/<key>.xgs` file whose key is the first 8 bytes of sha256 over the program's control section. A host integration therefore either ships genuine bundles or replaces `load_shader` with the SPIR-V the DMSH chain already produces; that decision is open, and so is everything past it: no NDK, arm64, Adreno, surface/swapchain, genuine bundle, pipeline or draw was run.
