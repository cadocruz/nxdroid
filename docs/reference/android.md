# Android: the vendored Vulkan engine

The Android port keeps the game's own AArch64 code and replaces the Metal replay (`dm/gfx/nvn/nvn_mtl.m`) with a Vulkan one. The replay engine and its `nvn_vk.c` adapter are not written here: they are vendored from [jhaizhou-ops/d2r-mobile](https://github.com/jhaizhou-ops/d2r-mobile) (MIT), a fork of this repository, at commit `1e0e7934c9ccdf95494aee5065d1d07ab3cc3918` (tag `v2.1.0`, committed 2026-10-28). Nothing in this page describes a working port: the tree is imported and pinned and it is not wired into any build. Only its engine was built and initialized, out of tree, on a desktop Linux machine, to measure what it needs ([The desktop smoke build](#the-desktop-smoke-build)); no NDK, device or Mac build has been run on it.

The import of 108 files keeps upstream paths so that a new upstream commit diffs mechanically:

| Path | Files | What it is |
|---|---|---|
| `dm/gfx/vulkan/` | 85 | The Vulkan replay engine and the `nvn_vk.c` adapter that implements this repository's `mtl_*` ABI (`dm/gfx/nvn/nvn_mtl.h`, `dm/gfx/nvn/nvn_obj.h`) |
| `dm/android/compat/` | 13 | Mach, `mach_absolute_time`, QoS, `clonefile`, CommonCrypto and malloc-zone shims for bionic |
| `dm/android/docker/` | 2 | The pinned Linux build environment (Ubuntu snapshot, NDK 29.0.14206865, CMake 3.31.6, Gradle 9.8.1, JDK 17) |
| `dm/android/` | 5 | `CMakeLists.txt`, `front_android.c`, `tools/asm_elf.py`, `vulkan_present.cpp`, `vulkan_present.h` |
| `dm/gfx/nvn/` | 2 | `nvn_copy_pitch.h` (copy stride and extent validation shared by the engine's copy paths) and `nvn_pool_flags_registry.h` (bounded host pool-flags lookup) |
| `dm/gfx/xtrace.h` | 1 | System timeline markers: HiTrace on HarmonyOS, empty elsewhere |

`dm/gfx/vulkan/INTEGRATION.md` (upstream's Chinese integration memo) and `dm/android/jni_android.c` (the D2R app shell: its Java activity, its `/sdcard/Download/S2X/...` data path, its 18 `.data` archives) are deliberately not imported. The imported engine has no title-ID branches; its one title-shaped piece is `xbg_game.cpp`'s camera-patch namespace (it recognises the main camera's constant blocks by content and skips one cull shader by key), which is off unless `DM_CAM` is set. Every imported file, its upstream commit, its sha256, its license and its local modification are recorded in `dm/tools/android_vendor.tsv`.

## The target device, measured

The target is a Galaxy S23 Ultra (`SM-S918B`, Snapdragon 8 Gen 2 for Galaxy, Adreno 740), Android 16 (SDK 36, security patch 2026-09-05), 12 GB. `dm/gfx/vk/probe/vk_probe.c` answers what the backend needs to know from the device itself, prints one `key = value` per line and is validated by `dm/gfx/vk/probe/tests/test_probe_output.py`, which is the contract (42 checks: dotted array indices, `driver_version` with three or four components plus `driver_version_raw`, three decimals on float limits, `device_selected`, an optional `exec_pages_errno`, `driver_info` exempt from the path and timestamp rules). Built for Android with `podman run --rm --userns=keep-id -v "$PWD:/src:rw" -w /src dm-android-tools:1 make -C dm/gfx/vk/probe android NDK=/opt/android-sdk/ndk/29.0.14206865` (`ANDROID_API ?= 24`: the NDK has no `libvulkan.so` stub below it), pushed with `adb push … /data/local/tmp/vk_probe`, run in `adb shell`, and the dump validated with `python3 dm/gfx/vk/probe/tests/test_probe_output.py <dump>`. On the device it is valid and byte-identical across runs.

## The pin and the gate

### `android_vendor.py --check` fails: a vendored file no longer matches its row

- **Symptom:** CI or a local run prints `[RED] android_vendor: <path>: sha256 … does not match the manifest (…)`, or `… is vendored but not in the manifest (run --write)`, and exits 1.
- **Cause:** the bytes under a vendored root changed, a file was added or removed there, or a row drifted from the pin in `dm/tools/android_vendor.py` (`UPSTREAM`, `COMMIT`, `TAG`, `DATE`). The manifest is the only record of what was imported: a changed byte without a changed row means the tree no longer describes its own provenance.
- **Fix:** read the diff first, then either restore the upstream bytes or (for a deliberate local change) run `--write` and put the reason in that row's `modifications` column; the tool keeps an existing row's metadata and only fills new rows. Updating upstream means changing `COMMIT`/`TAG`/`DATE`, running `--write`, and classifying every changed row as *take* (bug fix or driver knowledge), *skip* (specific to upstream's title) or *adapt* (touches this repository's ABI), with the reason in the commit message. Three rows carry a pending adaptation (their bytes are still upstream's today): `dm/android/CMakeLists.txt`, `dm/android/front_android.c`, `dm/gfx/vulkan/nvn_vk.c`.
- **Found on:** the `v2.1.0` import; `python3 dm/tools/android_vendor.py --check` is the gate and `dm/tools/tests/test_android_vendor.py` drives it on a synthetic tree.

The tool scans the three vendored roots recursively plus the five explicit `dm/android` files, so a new file under `dm/android/compat/`, `dm/android/docker/` or `dm/gfx/vulkan/` cannot be added silently. A file elsewhere under `dm/android/` is out of scope until it is listed in `FILES`. A sha256 does not cover the mode bit, so the one file that is executable upstream, `dm/android/docker/build.sh` (775), is checked separately; a copy that lost `+x` fails.

## The portability audit

`dm/tools/android_audit.py` answers "is this file portable to Android?" for the code the port moves: the C, Objective-C and assembly of `dm/host` and `dm/gfx/nvn`. It prints one line per finding — `path:line: category: text`, grouped by file and sorted — in four categories: `apple-api` (the Mach kernel and Darwin libc: `mach_*`, `vm_*`, `<mach/*>`, `getsectiondata` and `_mh_execute_header`, `os_unfair_lock`, `dispatch_*`, the `pthread_*_qos_class*` calls, `sysctl`, `clonefile`, CommonCrypto, `<TargetConditionals.h>` and `TARGET_OS_*`, `<libkern/*>`, `os_proc_available_memory`, and Darwin's ucontext register layout), `objc-framework` (an Apple framework header, an `@`-keyword, an `NS*`/`CF*`/`MTL*`/`GC*`/`CM*`/… type or `id<protocol>`), `page-assumption` (a `16384`, `0x4000`, `1 << 14` or `16 KiB` literal on a line that also talks about a page, `mmap`, `mprotect` or `getpagesize`: a candidate, because the same literal is also used for guest and device constants) and `macho-section` (`section("__DATA,swhle")`, `__TEXT,__text`, `-sectcreate`).

`dm/tools/android_audit_baseline.tsv` is the record of what is Apple-specific today, keyed by file, category and the sha1 of the whitespace-normalised line, so reformatting a file or moving a hit does not invalidate it. `--check`, the command CI runs, fails on a hit that is not in the baseline **and** on a baseline row whose hit is gone: the list only shrinks. `--summary` prints the counts per category and the ten files with the most hits, `--json` one object per hit, `--all` also scans `dm/gfx/metal` and `dm/gfx/vk` for the report. Out of scope, by rule: the vendored trees (`dm/third_party`, `dm/gfx/vulkan`), the probe and the engine smoke harness, and every `tests/` directory — another repository's code, or diagnostics that are not shipped.

Two things the audit does not itemise, because the unit is the file: the Apple types inside a `.m` file (an Objective-C implementation file is Apple-only as a whole; `nvn_mtl.m` alone would add thousands of `MTL*` lines that say nothing new) and the `_`-decorated symbols of a `.S` file (`entry.S`, `nvn_entry.S` and `nvn_thunks.S` are Mach-O assembly throughout, so assembling them for ELF is a whole-file change). `dm/tools/tests/test_android_audit.py` drives every category, the normalisation, the exclusion list and both kinds of failure on a synthetic tree.

### The device page is 4 KiB and `nvn_dirty.c` already follows it

`dm/gfx/nvn/nvn_dirty.c` tracks coherence per page, so the page size decides whether it is correct on a 4 KiB device. It takes the page from `getpagesize()` (`:128`), rounds every pool to it (`:148`), and protects, unprotects and stamps in units of it (`:77`, `:107`, `:182`, `:202`), so it needs no change: on the Galaxy S23 Ultra a pool simply spans four times as many pages. The two 16 KiB mentions in that file are comments that no longer describe the code — `:27` ("ranges are rounded to host pages (16 KB)") and `:99` ("one system call per 16 KB page", whose measured call count is a quarter of what 4 KiB pages cost). The other `0x4000` sites are not host-page assumptions: `dm/host/loader.c:212` and `:214` are the rewriter's 16 KiB key page (a guest on-disk format), `dm/host/hle_svc.c:574` and `dm/gfx/nvn/nvn_mtl.m:1740` round to `getpagesize()` and only say 16 KB in the comment.

One site does depend on it: `dm/host/probe.c:168`-`:171` aligns the probe instruction down to 16 KiB and calls `mprotect` on 0x4000 bytes. That protects up to three pages the probe does not own, and fails (`ENOMEM`, then `die("probe mprotect")`) when one of them is not mapped — inferred from the code, not seen failing. The safe form is the one the watch path already uses at `:355`: `uint64_t pg = at & ~(uint64_t)(getpagesize() - 1); mprotect((void *)pg, getpagesize(), prot)`.

## Adreno driver gates

### The Adreno 740–799 family loses the device on the quad-derivative and warp32 rewrites

- **Symptom:** on a Snapdragon 8 Gen 2 or 8 Gen 3 phone the app dies about two seconds into the boot, before the main menu: dmesg shows `gpu timeout ... status 00EF1087` (a kgsl GPU page fault) and the next submit returns `VK_ERROR_DEVICE_LOST` (-4).
- **Cause:** the SPIR-V of two shader rewrites written for Adreno 730 (`xbg_spirv_quad`, `xbg_spirv_warp`) is accepted but faults in the Adreno 740–799 driver; both run on 730 and 830. See [upstream issue #141](https://github.com/jhaizhou-ops/d2r-mobile/issues/141).
- **Fix:** `xbg_adreno_policy.h` reads the model from the Vulkan device name (`Adreno (TM) 740` → 740; anything that is not three digits is unrecognized) and, for vendor `0x5143` and model 740–799, defaults both rewrites off; a marker file (`gfx-quad-derivatives`, `gfx-warp32`) still turns either on explicitly. The precedence is marker file, then device family, then `DM_GFX_QUAD_DERIVATIVES` / `DM_GFX_WARP32`: the device check must come first because the Android JNI sets both environment variables to 1 on every phone. The log line is `NVN Adreno 740/750 (device "..."): the quad-derivative and warp32 rewrites default off; a marker file still turns either on`.
- **Found on:** upstream's reports, not reproduced here. The target device (Galaxy S23 Ultra, Adreno 740) is in this family, so the gates apply to it by default.

### Adreno 750–799 segfaults while building a pipeline from a subgroup helper

- **Symptom:** pipeline creation crashes inside Qualcomm's `libllvm-qgl.so` at address `0x48` for shaders whose subgroup instructions sit in a called helper function, on Samsung and Xiaomi Snapdragon 8 Gen 3 phones.
- **Cause:** a driver compiler defect in the Adreno 750–799 family ([upstream issues #123](https://github.com/jhaizhou-ops/d2r-mobile/issues/123), [#153](https://github.com/jhaizhou-ops/d2r-mobile/issues/153), [#166](https://github.com/jhaizhou-ops/d2r-mobile/issues/166)).
- **Fix:** when the engine loads such a shader it inlines the helpers into the entry point (the import pack is unchanged). The marker file `gfx-inline` forces it on or off; on this family it defaults on, and it is only compiled when `XBG_HAVE_SPIRV_OPT` is defined. Without SPIRV-Tools the code logs `NVN helper inlining is not built into this package; shaders load as they are` and turns the workaround off — so a build that drops SPIRV-Tools also drops the only mitigation for these phones.
- **Found on:** upstream's reports; not reproduced here. The Adreno 740 is outside this family but is in the 740–799 rewrite-gate family above, so the two gates do not overlap on our target.

## The ABI and host gaps

### The vendored replay does not link against this repository's `nvn_mtl.h`

- **Symptom:** linking `dm/gfx/vulkan/nvn_vk.c` into the host would report undefined references for 27 entry points this repository declares, and the objects the replay layer expects are not the ones this repository lays out.
- **Cause:** the two `nvn_mtl.h` headers diverged in both directions after the fork point. This repository declares 27 entry points that upstream's `nvn_vk.c` does not define: 12 of the 29 `nvn_mtl.h` declares (`mtl_alias_drop_pool`, `mtl_device`, `mtl_device_classic`, `mtl_ext_tex`, `mtl_present_ext`, `mtl_queue_activate`, `mtl_queue_forget`, `mtl_set_depth_zero`, `mtl_set_origin_lower_left`, `mtl_set_queue_origin_lower_left`, `mtl_wait_acq`, `mtl_vbuf_stats`) and 15 that only `nvn_obj.h` declares (`mtl_ab_gpu`, `mtl_cpu_tex_count`, `mtl_link_rate`, `mtl_link_stalled`, `mtl_link_tick`, `mtl_link_wait_ticks`, `mtl_pkg_edge_skips`, `mtl_present_test_stall`, `mtl_reg_image`, `mtl_snap_acquire_wait`, `mtl_snap_on`, `mtl_sub_fill`, `mtl_tex_cpu_written`, `mtl_tex_gpu_owned`, `mtl_tex_init`). `mtl_present_wait`, counted as a 13th before this was measured, is in fact defined by the adapter (`nvn_vk.c:83`). In the other direction `nvn_vk.c` defines 12 `mtl_*` functions neither header declares, two of them D2R-specific (`mtl_ui_ghost`, `mtl_ui_ghost_rect`): inert for linking, but they show the two sides were written against different headers. One signature differs in its types: `int mtl_link_wait_tick(int vsyncs, uint64_t timeout_ns)` here against `int mtl_link_wait_tick(uint64_t timeout)` in the adapter, so the caller's `vsyncs` argument lands in `timeout`. `nvn_obj.h` differs too: upstream's `queue_t` has no `origin_ll` or `serial`, its `tex_t` has no `snap` and no builder swizzle/depth-stencil state, its `prog_t` has no `snap`, and its `view_t` and `samp_par` are packed differently (the 16-byte `NVNtextureView` of newer SDKs, and a sampler `reduction` byte).
- **Fix:** none here; reconciliation belongs to the integration sprint and is recorded in the `nvn_vk.c` row of `dm/tools/android_vendor.tsv`. Deleting either side's entry points blind would change the Metal path or the replay path silently, so the union has to be decided against `nvn_mtl.m` and the Vulkan replay together.
- **Found on:** `dm/gfx/vk/engine_smoke/abi_gaps.py`, which parses both headers and `nvn_vk.c` symbol by symbol and names the `nvn_mtl.m` section that implements each missing entry point; its output is `abi_gaps.txt`. The link itself was not run.

### The vendored replay reads the fork's command records, and this repository writes a newer set

- **Symptom:** the first `ClearBuffer`, `DepthClamp`, render-conditional, fence-sync, transform-feedback or per-slot descriptor bind ends the process: the replay has no case for the opcode and calls `xbg_fatalf("NVN opcode %u ... not implemented")`.
- **Cause:** `dm/gfx/nvn/nvn_obj.h`'s op enum agrees with upstream's for 0..38 and then diverges. This tree continues with `OP_CLEAR_BUF`(39), `OP_DEPTH_CLAMP`(40), `OP_RENDER_COND`(41) … `OP_BIND_VBUF1`(50); the fork continued with `OP_COPY_IMAGE_STRIDE`(39) and `OP_COUNT_`(40). `xbg_game.cpp:3766`'s dispatch has no case for 12 of our 51 ops (`OP_CLEAR_BUF`, `OP_DEPTH_CLAMP`, `OP_RENDER_COND`, `OP_FENCE_SYNC`, `OP_TF_BIND`, `OP_TF_STATE`, `OP_RAST_DISCARD`, `OP_VP_SWIZZLE`, `OP_BIND_TEX1`, `OP_PRIM_RESTART`, `OP_BIND_UBO_SMALL`, `OP_BIND_VBUF1`), so each reaches the fatal at `:3839` — a loud stop, not silent corruption. The engine's own nine extension ops are written at the *symbol* `OP_COUNT_+1..+9`, which compiles to 52..60 against this tree's enum and 41..49 against the fork's; adding `OP_COPY_IMAGE_STRIDE` at 39 without extending the enum first would shadow `OP_CLEAR_BUF` and still leave those nine cases one place off. Payloads moved as well for ops both sides do implement: our `p_draw` carries `instances`, `base_instance`, an indirect address and a multi-draw count that the engine's `{prim, first, count}` does not (and `hle_nvn.c` records only 0x20 bytes for a plain or instanced draw, where the handler's `payload<p_draw>` demands 48), our `p_dispatch` carries an indirect address it ignores, our `p_bind_handles` carries `defer` and `src` ahead of `h[32]` (the engine now compiles against this header, so its offset 24 is right; the live defect is the 128-slot table), our `p_copy_stride` has the per-image flag it ignores, and `queue_t` / `tex_t` / `view_t` / `samp_par` / `cmd_t` carry fields the fork's do not.
- **Fix:** partly done. The enum now carries the fork's extension names in this header, after this tree's `OP_COUNT_` (51): `OP_XBG_SYNC_WAIT` (52) .. `OP_XBG_TYPED_CLEAR` (60), plus `OP_XBG_COPY_IMAGE_STRIDE` (61) and `OP_XBG_PATCH_SIZE` (62). The engine's `OP_COUNT_+N` labels were left as they are (they now name those ops), one compatibility block at the top of `xbg_game.cpp` maps its `OP_COPY_IMAGE_STRIDE` spelling, and its tessellation `case OP_COUNT_:` — 51 is this host's sentinel and no command of ours — became `case OP_XBG_PATCH_SIZE:`. `xbg_game.cpp` therefore compiles against this header with no workaround ([the entry below](#xbg_gamecpp-compiled-as-c-fails-on-nvn_objhs-helpers-and-on-the-forks-opcode)). What remains is the port itself, listed mechanically in `dm/gfx/vk/engine_smoke/opcode_map.txt` and `payload_mismatch.txt`: **51 ops, 39 handled, 12 missing** (`OP_CLEAR_BUF` .. `OP_BIND_VBUF1`; the map names the `nvn_mtl.m` section to port for each), and **two open disagreements** between the two readers of the ops both implement: `P6`, where a record with `first != 0` or `n > 1` is refused because the pipeline declares one viewport, and `P8`, where the barrier's cache bits are ignored because the reader's single full barrier is stronger. In both the writer is ground truth — `hle_nvn.c` is what 93 profiles record through and what games size with `GetCommandMemoryUsed` — so the reader is what moves. Six were closed here: `P1`/`P2` (a compact draw record is 24 / 32 bytes, and the handler now reads through `draw_rec` / `draw_idx_rec`, which give the fields the writer did not store as 0), `P3` (indirect dispatch reads its group counts at execution from the recorded address), `P4` (the per-stage handle table is `tex[6][256]`, so the separate textures at slots 128..255 bind), `P5` (`OP_COPY_STRIDE` branches on `p_copy_stride.image`) and `P7` (a `Downsample` reaches `resolve_texture` instead of a `vkCmdCopyImage` that cannot read a multisampled source). The compact draw lengths are now pinned in `dm/gfx/nvn/nvn_obj.h`: `DM_REC_DRAW_COMPACT` / `DM_REC_DRAW_IDX_COMPACT` are what `rec_draw` / `rec_draw_idx` write and what `draw_rec` / `draw_idx_rec` read, and the assertions beside them fail the build when a field moves inside `p_draw` or `p_draw_idx` — the class of bug `P1`/`P2` was, caught by `make -C dm/gfx/vk/engine_smoke report` instead of by a game.
- **Found on:** `dm/gfx/vk/engine_smoke/` — `opcode_map.py --check` derives the table from the enum, the dispatch in `xbg_game.cpp`, the writers in `dm/gfx/nvn/*.c` and a compiled payload-size probe, so it cannot drift from the tree; the dispatch was also read against both enum spaces, one of them from upstream's pinned `nvn_obj.h`, fetched read-only and not imported.

### `xbg_game.cpp` compiled as C++ fails on `nvn_obj.h`'s helpers and on the fork's opcode

- **Symptom:** the Android toolchain, clang, reported 10 errors on `xbg_game.cpp`: `cannot initialize return object of type 'const p_bind_vbuf *' with an lvalue of type 'const void *'` at `dm/gfx/nvn/nvn_obj.h:130`, then `:131`, `:138`, `:139`, `:151`, `:152`, `:167` and `:168`, and `use of undeclared identifier 'OP_COPY_IMAGE_STRIDE'` at `xbg_game.cpp:3812`. GCC reported the same at the first site and refused its own `-fpermissive` there.
- **Cause:** five helpers in `dm/gfx/nvn/nvn_obj.h` (`vbuf_rec`, `bind_buf_rec`, `bind_rec`, `draw_rec`, `draw_idx_rec`) returned or assigned a `const void *` as a typed pointer, eight times — implicit in C and not in C++ — and `xbg_game.cpp` includes that header through `xbg_game_internal.h`'s `extern "C"`; the other error was the opcode above, whose number the fork's enum gives a different name.
- **Fix (resolved):** explicit casts at the eight sites, which is invisible to the C users (the record layouts are identical, so the cast states what the function already promised); an `extern "C"` guard and a `DM_STATIC_ASSERT` on both headers that is `_Static_assert` in C and `static_assert` in C++; and the fork's opcodes named after `OP_COUNT_`, which `xbg_game.cpp` reaches through one compatibility `#define` ([the entry above](#the-vendored-replay-reads-the-forks-command-records-and-this-repository-writes-a-newer-set)). `make -C dm/gfx/vk/engine_smoke report CXX=clang++ CC=clang` compiles both headers as C and as C++ with `-Werror` and all 24 translation units (`xbg_game.cpp` included) with no `-fpermissive` and no `-D`; the same build is green with gcc/g++. The vendored file's edits are that `#define` block, one `case` label, the 256-slot texture table with the two descriptor readers that index it, and the viewport state (`viewport[16]`, `depth_range[2]`, `viewport_n`) with its consumers; every one is recorded as `adapt` with its reason in `dm/tools/android_vendor.tsv`.
- **Found on:** `dm/gfx/vk/engine_smoke/report.sh` (one line per translation unit) and its `headers` target.

### The imported files need headers this repository does not have

- **Symptom:** the imported translation units cannot compile as a set: missing include files, and `dm/android/CMakeLists.txt` cannot configure.
- **Cause:** upstream added files after this repository's fork point that are outside the import scope. The three the engine itself needs are imported: `dm/gfx/xtrace.h` (included by `xbg_game.cpp` and `vulkan_present.cpp`), `dm/gfx/nvn/nvn_copy_pitch.h` (included by `xbg_game.cpp` and `xbg_bc_policy.h`) and `dm/gfx/nvn/nvn_pool_flags_registry.h` (included by `tests/pool_flags_registry_test.c`). The four that remain are the touch/iOS path: `front_android.c` includes `dm/android/touch_android.h` and `dm/ios/Sources/dm_touch_game_state.h`, and the CMake build needs `dm/android/tools/host_sources.py` and `dm/ios/tools/overlay_contract.py`; it also wants `dm/third_party/spirv-tools` and the app sources (`jni_android.c`, `touch_android.c`, `text_input_jni.c`, `overlay_validate.c`, the `app/` Gradle project), none of which are imported.
- **Fix:** open for the touch/iOS set, which comes in with that work. The three headers arrived in the second import round: `dm/gfx/` is this repository's own directory, so they are listed one by one in `FILES` in `dm/tools/android_vendor.py` rather than by adding `dm/gfx/nvn` as a vendored root, which would sweep our own headers into a manifest of another repository's files. ## The desktop smoke build

`dm/gfx/vk/engine_smoke/` builds the engine alone on Linux x86_64 — system Vulkan headers, GCC 15.2 or clang, Mesa lavapipe or the machine's GPU — links it to a 60-line harness that creates the instance, device and queue `xbg_game_config` asks for, and prints the per-translation-unit state plus the `mtl_*` gap above. The engine sources are compiled in place; the one local edit they now carry (`xbg_game.cpp`'s compatibility block) is recorded in the manifest, so it stays green. Its [README](../../dm/gfx/vk/engine_smoke/README.md) carries the commands and every measured line; what it established:

- All 8 C files and all 12 C++ files compile with `-Wall -Wextra`, under gcc 15.2 / g++ and clang 21.1.8 / clang++, with no workaround and no `-fpermissive` (`xbg_texture.c` needs `-D_GNU_SOURCE` on glibc, which declares `pthread_setname_np` only under `__USE_GNU`; bionic declares it unconditionally). `dm/gfx/nvn/nvn_obj.h` and `nvn_mtl.h` also compile alone as C and as C++ with `-Werror`.
- `build/engine_smoke` prints `xbg_game_initialize -> 0` and `xbg_game_shutdown -> 0` and exits 0 on Mesa 26.0.8 lavapipe (`llvmpipe`, api 1.4.335) and on an RTX 5060 Ti (api 1.4.312), with 60 and 63 engine log lines and no fatals.
- Initialization needs neither guest memory nor a shader bundle. Its only inputs are a non-NULL physical device, device and queue, a `shader_directory` string, a non-zero fence timeout (`xbg_game.cpp:3886`), a queue family with `GRAPHICS` and `COMPUTE` (`:3906`) and the features `enabled_core` asks for (`:3905`). A bundle is read lazily at the first program bind, and `load_shader` then fails loudly (`xbg_game.cpp:1980`, `Missing genuine shader bundle %s`, then the length, header and exact-extent checks at `:1981`–`:1983`) on a `<shader_directory>/<key>.xgs` file whose key is the first 8 bytes of sha256 over the program's control section. A host integration therefore either ships genuine bundles or replaces `load_shader` with the SPIR-V the DMSH chain already produces; that decision is open, and so is everything past it: no NDK, arm64, Adreno, surface/swapchain, genuine bundle, pipeline or draw was run.
