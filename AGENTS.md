# Notes for agents

- This repository runs Nintendo Switch games natively on Android (arm64-v8a, Vulkan): the game's own code runs, rewritten only where the platform requires it (`dm/tools/patch_nso.py --target=android`), on a host that answers Horizon's SVCs and the SDK's services (`dm/host`, with the bionic layer in `dm/android`), and NVN is replayed on Vulkan (`dm/gfx/vulkan`). The target device is a Samsung Galaxy S23 Ultra (Adreno 740). [HANDOFF.md](HANDOFF.md) is the state of the port: what runs on the device, what is broken, what to do next, and the commands of the gates. The [games table](dm/games/README.md#games) lists the profiles nxdroid inherited from nxnative, each with its build, SDK, engine and graphics API and its note, `dm/games/<id>/README.md`; a game counts as running on Android only when its note says so. [README.md](README.md) is the player-facing page (building the APK, preparing a game, playing); [docs/development.md](docs/development.md) has the internals and the build. The Apple sources (`*.m`, the Metal replay `dm/gfx/nvn/nvn_mtl.m`, the iOS and Mac apps) stay in the tree until HANDOFF.md §8 item 10 removes them: `nvn_mtl.m` is still the reference the Vulkan engine and the `opcode_map` / `abi_gaps` gates are checked against. Do not build for or test on Apple platforms.

- Where a new finding goes, once: a fact about one game (its passes, shader keys, measurements, why its profile needs a key or a cut, its status on Android) in that game's note, in the section it belongs to and marked current or resolved; a general mechanism (a host, engine or tool change that holds for other games) as an entry in its `docs/reference/<subsystem>.md` section (Symptom, Cause, Fix, Found on with the game's note linked), then `python3 dm/tools/docs_symptoms.py` to update the symptom index, and a line under the game note's "Found on this game". The state of the port and its open list go in HANDOFF.md. Link to a finding instead of repeating it. Adding a game takes its note and its row in the games table. This file changes only when a rule does; it states no game count (the games table is the count). `dm/tools/tests/test_docs.py` checks the links and anchors, the notes and their table rows, the symptom index, and the length of this file (1,500 words) and of each guide in `docs/agents` (6,000).
- Each game's constants and shader tables form a game profile in `dm/games/<id>/`, where `<id>` is the base game's title ID: `game.tsv` plus the tables (and `patches.py` when the rewriter has patches for its builds). Tools pick the profile with `DM_GAME`; the Android build picks it with `-DGAME=<id>` (CMake) or `-PdmGame=<id>` (Gradle), and `prepare_game_android.py` with `--title-id`. There is no default game: set it every time (the tools stop and list the profiles otherwise). Put per-game values in the profile, not in code ([dm/games/README.md](dm/games/README.md)).
- Prefer general optimizations and fixes to game-specific rules. Performance work (frame pacing, power, caches, load times) counts here as much as correctness. First look for a change that holds for every game: Horizon / NVN / Vulkan semantics, or what the binary, its SDK version, its imports or its files show. Use a game-specific rule (a profile key, a rewriter cut, a build-ID gate, a per-game branch in the host) only when no general rule can do it. A rule for one GPU or driver (the Adreno gates in `dm/gfx/vulkan/engine/xbg_adreno_policy.h`) follows the same test: keyed by what the device reports, with the fault it avoids written next to it.
- Find a bug's root cause and fix it there; do not just work around it. Before changing code, find why it happens: the faulting instruction and its decompilation, the value that went wrong and who wrote it, the Horizon / NVN / Vulkan semantics the host or the engine gets wrong. Then fix that place. A change that only hides the symptom (a stub, a skipped call, a clamp, a retry, a sleep or a longer timeout, a cache flush, a switch that turns a feature off) is a workaround: use one only when the cause is known and lies where it cannot be fixed (the game's own code, which a rewriter cut changes deliberately, or a platform or driver limit), or when the user asks for a stopgap. Then say so in the code comment and in the game note or reference entry: the cause, or what is still unknown, marked open.
- Per-build knowledge is keyed by the NSO build ID: rewriter cuts, observation gates and frame-step stubs in the profile's `patches.py` (a game's own modules) or `dm/tools/sdk_patches.py` (Nintendo's `sdk` modules), which `dm/tools/patch_nso.py` loads, the profile's `build` rows, and host behaviour that uses fixed module addresses checks `module_t.build_id` (from `fixups.tsv`; `dm_main_build()`). When a new game build appears, carry addresses over with `dm/tools/nso_fnmap.py` and check them by disassembly; never let fixed addresses run on a build they were not found in. For automatic cuts across updates, opt individual patches into `MATCH_CUTS` only after verifying their function fingerprints and assumptions ([Function-matched cuts](docs/reference/rewriter.md#function-matched-cuts-for-unregistered-builds)).
- A module rewritten for Android (`--target=android`) cannot run on the Apple host and the reverse: the loader refuses a module of the other target. `scripts/prepare_game_android.py` always rewrites with the Android target.
- Scripts the user runs live in `scripts/` at the repository root. Each one runs from a terminal (non-zero exit on error). Tools that only agents or other scripts call stay under `dm/`.
- Game files, keys and anything extracted from them never go into this repository, its CI or an issue: they stay next to the game (the `<game>-work` folder `prepare_game_android.py` writes beside it, and the prepared output) and on the device. Do not print key values.
- Language: everything is in English: `README.md`, docs, code comments, log messages, script output and other files. Red log lines (something unimplemented or wrong) start with `[RED] `. Text that must match a game's own Chinese data is written as escapes (`"\xE8\xB5\xB7"`), never as characters.
- The shader translation chain has one version for every game, `DMSH_CHAIN` in `dm/gfx/nvn/dmsh_chain.h`. It covers the chain's tools (`dm/gfx/tools/dmsh_*`, `Program.cs`, `dm/gfx/nvn/dmsh_abi.h` and `dmsh_chain.lock`). A profile's own inputs (`shader_map.tsv`, `shader_facts.tsv`, `shader_pairs.tsv`, `bf_want.tsv`, its `shader_*` / `nvn_*` keys) are not part of it. After changing a chain tool, run `dmsh_chain.py --header` once and commit `dm/gfx/nvn/dmsh_chain.h` with the change (`dm/tools/tests/test_nsp_chain.py` fails on a stale one); then prepare the games it reaches again with `prepare_game_android.py --rebuild-shaders`, which translates their shaders to SPIR-V with `dmsh_xlate` and writes the `.xgs` bundles the engine loads.
- Vendored code (the Vulkan engine in `dm/gfx/vulkan`, the bionic layer and build environment in `dm/android`) is listed with its upstream pin and sha256 in `dm/tools/android_vendor.tsv`: an edit to a vendored file updates its row (the LF bytes' sha256, by hand; `android_vendor.py --write` would also rewrite the rows of files it should not), and `android_vendor.py --check` must stay green.
- CI (`.github/workflows/tests.yml`, Linux) runs the gates of HANDOFF.md §5 and an NDK build of `dmhost` and `libdm.so` on every push and pull request; both must stay green. CI never runs on a device: a change that reaches the replay, the host or the shaders says in its PR which games were run on the device and what was compared (log lines, `NVN PERF`, screenshots), or that none were.
- The user builds and installs the APK and runs the games on the device; diagnostics come back as `adb logcat -d -s dm` and screenshots. Do not install builds on the user's devices or change files on them unless the user asks. Ask before downloading or installing anything on the user's machine.
