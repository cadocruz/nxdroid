# Mario Kart 8 Deluxe (`0100152000022000`)

Updates 4.0.0 (v1441792) and 4.0.1 (v1507328) over the base game, SDK 4.4.0, the oldest SDK until [Bayonetta 2](../01007960049A0000/README.md)'s 3.6.0. Nintendo's sead / agl / gsys engine with NintendoWare (G3d, Ui2d, Vfx, Atk) and Pia networking, on NVN. Modules `main`, `subsdk0` (the SDK's movie library: the menus' H.264 previews) and `sdk`. RomFS is mostly Yaz0-compressed SARC (`.szs`), BFRES models and BNTX textures, which the game reads itself. Plays on the iPhone (A20 Pro): 60 fps docked with about 6 ms of GPU time a frame, a 2.4 GB footprint with 3.7 GB of headroom, no audio underruns. Mii heads draw nothing (no firmware); see [Miis](#miis).

The 4.0.1 build has the same `subsdk0` and `sdk` build IDs as 4.0.0 and a different `main` build ID. This profile has no build-specific function patches. [A 4.0.1 iPhone report](https://github.com/seedds/nxnative/issues/281) covers the title, menus and a complete three-lap Grand Prix race after the shared notification-wait fix. A second 4.0.1 build from current upstream, with Booster Course DLC and a derived profile, completed a full race on an iPhone 15 Pro Max (iOS 27.0.1) and on a Mac. The registered profile's combined shader tables and Mac build passed shader and pipeline prebuild checks; gameplay on a build made from this registered profile has not yet been tested. A build from the registered profile needs both update NSPs in the input folder.

Brought up on the Mac from 4.0.0: boot, the title with its demo race, the Mii pick, the menus (their movie previews play), a 50cc Grand Prix race at Mario Kart Stadium to its results, and a second boot that loads the save. 60 fps (p50 16.7 ms), sound; about 2.4 GB resident and 1.26 GB of Metal allocations in the race, flat over minutes.

## Android (S23 Ultra)

The Mac and iPhone results above are nxnative's. On Android this is the one game run so far, on a Samsung Galaxy S23 Ultra (Adreno 740, Android 16) with update 4.0.1, prepared by `scripts/prepare_game_android.py` and started from the app (`com.nxdroid`); the state of the port and every run are in [HANDOFF.md](../../../HANDOFF.md) (Status, "Next device session", §8 item 12).

- **Current:** it boots, plays its menus and their H.264 previews (`AMediaCodec`), has sound (AAudio) and races. The 2D interface and the videos are right. **The 3D race rendering is visually clean and complete on the device, locking a full 60.01–60.22 FPS across the race-start grid (Run 36, 2026-11-07)**: clicking OK enters the race without crashing, road, kart and textures render correctly, and GPU time is down to `gpu_ms = 5.97–10.08 ms` (>1.6x headroom for 60 fps). Race performance reaches steady locked 60 FPS with safe 1-frame boundary pipelining in `xbg_legacy_wait` (zero fence stalls, `legacy_wait = 0.00 ms`); menus reach 60.
- **Ruled out on the device (2026-11-03), one marker at a time from a clean state:** `gfx-noload`, `gfx-read-preflight`, `gfx-tex-dirty`, `gfx-wb-skip`, `gfx-upload-prologue`, `gfx-vcache`, `gfx-pipe-memo`, `gfx-native-bc`, `gfx-forward-temps`, `gfx-ldc-fold` (no change to the picture; `gfx-read-preflight` on cost about 50–74 ms of submit time a frame). The swapchain is sRGB (`format=43 source_srgb=1`).
- **Found while tracing:** `CopyBufferToTexture` writes small dynamic textures (`512x608` format `0x1`, `256x304` format `0xd`) into pool ranges that GPU-written render targets (`1920x1080` format `0x3d`, `960x540` format `0x25`, `1280x720`) also cover; the engine's experiments that re-uploaded those targets did not fix the picture and are off by default (`gfx-alias-invalidate`).
- **Ruled out on the device (2026-11-04), runs 20 to 25:** the depth converted twice (`gfx-depth-clip` = `0`, then a re-pack without the vertex-shader rewrite: the game keeps NVN's GL depth mode and the engine converts it with `VK_EXT_depth_clip_control`; the packing now converts nothing by default), and attaching once a texture the game attaches at two colour slots (it does: slots 3 and 4, a `1920x1080` format `0x3d` target, write masks `0xf` and `0`; `gfx-rt-dedupe` = `1` changed nothing). The re-pack found 29,651 shaders and left 9 without a bundle. Only the pool-alias invalidation (`gfx-alias-invalidate`) changed the picture: the geometry was more complete and less displaced, the speckle and black areas stayed. Its `CopyBufferToTexture` part is on by default since `85031c7`; that this part alone gives the improvement is not yet shown on the device.
- **Ruled out on the device (2026-11-05), runs 26 and 27:** CPU writes to GPU-drawn texture storage after the GPU (the engine detected two such targets: `1920x1080` fmt `0x3d` and `960x540` fmt `0x25`; re-uploading from guest memory with `gfx-cpugpu-refresh=1` did not fix the 3D scene and worsened black regions from 16.5% to 25.9%). Also confirmed absent: `stencil-mode texture read as depth` and `sampler compare mode does not match`; device-backed `NVN_DEVICE_INFO_MAX_VIEWPORTS` operates cleanly.
- **Root cause found (2026-11-06, RenderDoc 1.47 frame capture):** GPU capture on the Galaxy S23 Ultra isolated the corruption to missing samplers in the material and lighting pass (`Colour Pass #6`, draw 2425). In `scripts/prepare_game_android.py`, `_inspect_image_type` had a flow-control defect that caused all combined image samplers (`OpTypeSampledImage`) to be recorded with descriptor type 2 (`VK_DESCRIPTOR_TYPE_SAMPLED_IMAGE`) instead of 1 (`VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER`). Consequently, the Vulkan replay engine never created or bound a sampler for any texture (`ii.sampler = VK_NULL_HANDLE`), causing Adreno 740 texture sampling instructions to fail (black track, black kart, speckling). Fixed in `prepare_game_android.py` and all 27,869 `.xgs` bundles batch-updated locally.
- **Race-start sampler crash resolved (2026-11-07):** after pushing `.xgs` bundles with descriptor type 1 (`COMBINED_IMAGE_SAMPLER`), the startup and title screen rendered with correct filtering, but entering a 3D race aborted immediately with `NVN sampler linear filtering unsupported ...`. The cause was `sampler_slow` encountering unsupported linear filtering and PCF on Adreno 740 for `VK_FORMAT_D32_SFLOAT`, `VK_FORMAT_R32_SFLOAT`, and `VK_FORMAT_R32G32B32A32_SFLOAT`, compounded by `null_texture` using `0x34` (`D32_SFLOAT`) for dummy depth textures. Resolved by switching dummy depth to NVN `0x32` (`D16`, widened to `X8_D24_UNORM_PACK32`), clamping unsupported linear/anisotropic filtering to `VK_FILTER_NEAREST` with a one-time log instead of calling `xbg_fatalf`, separating shadow flags in `ImgKey::kind`, and clearing stale pipeline cache files (`/sdcard/nxdroid/vk-pipeline-*.bin`).
- **Run 29 device verification & 60 FPS CPU optimization pack (2026-11-07):** on Galaxy S23 Ultra, live race rendering was confirmed visually clean with no corruption or crashes. Telemetry (`draws=1095.9/frame`) measured `gpu_ms = 5.97–8.40 ms`, proving the Adreno 740 is well capable of 60 FPS. Frame pacing was bounded by CPU submission (`14.95–21.89 ms`): (1) `legacy_waitall = true` on Android caused synchronous `vkWaitForFences` stalls (`legacy_wait_total = 10.23–12.40 ms/frame`); (2) `OP_BARRIER` unconditionally split open render passes 72.4 times/frame (`pass_ends op28 = 72.4/frame`, `passes = 103.1/frame`); (3) sampler and texture registrations caused false generation bumps and descriptor memo purges (`xmemo_drops = 581`, `retire = 3.31 ms/frame`). Resolved in `xbg_game.cpp` by enabling asynchronous fence retirement (`legacy_waitall = false`, `completion_wait_default = true`) on Android, coalescing `OP_BARRIER` passes by tracking `open_pass.shader_writes` matching `nvn_mtl.m`, and only bumping memo generations on true mutations of existing resources.
- **Pipeline warm-up failure resolved (2026-11-07):** `NVN PERF` reported `warm_built=0 warm_failed=974` and mid-race `[longframe]` compilation hitches (`new_pipes=38 pipe_compile=480.7ms`). Cause: `xbg_graphics_pipeline_key()` serialized 6 words for the viewport state (including `negativeOneToOne` for `VK_EXT_depth_clip_control`), but `warm::build()` only read 5 words, shifting deserialization by 4 bytes and causing `r.i != r.n` on 100% of pipeline records. Fixed by deserializing `neg11` and attaching `VkPipelineViewportDepthClipControlCreateInfoEXT` in `warm::build()`, restoring warm pipeline precompilation and eliminating mid-race shader compile hitches. The app also features an on-screen real-time FPS/performance HUD overlay (`mFpsOverlay` in `MainActivity.java`: FPS, frame time, GPU time).
- **Run 31 telemetry and 60 FPS pacing optimizations (2026-11-07):** live race telemetry (`/tmp/mk8dx_race_perf_run31.log`) confirmed the `warm::build()` fix succeeded 100%: `warm_built=1058 warm_failed=0`, with `created=0 create_ms=0.0` during the race. However, race framerate hovered at 28–39 FPS (`25.4–37.8 ms/frame`) despite `gpu_ms = 6.00–10.28 ms` due to two bottlenecks: (1) `mtl_wait_acq` forwarded to `mtl_wait` in `nvn_vk.c:78`, synchronously blocking the guest CPU on previous frame fences (`legacy_wait = 5.09–9.24 ms/frame`); fixed by returning `1` immediately in `mtl_wait_acq` since present semaphores and FIFO submission already guarantee CPU/GPU synchronization; (2) MK8DX finalized and re-initialized ~4–5 transient render targets per frame at identical pool addresses, causing `xbg_legacy_tex_release_now` to destroy images and framebuffers on release (`retire = 2.01–3.54 ms/frame`, `fb_creates = 4.0–5.0/frame`, `memo_bump[2] = 10,829`); fixed in `xbg_game.cpp` by retaining released pool-backed render targets in a bounded `released_images` list and re-adopting them in `get_image_slow`.
- **Run 32 telemetry and Run 33 crash analysis (2026-11-07):** live race telemetry (`/tmp/mk8dx_race_perf_run32.log`) confirmed the `released_images` cache eliminated per-frame framebuffer and image churn: `retire` dropped from `3.09–3.54 ms/frame` down to `0.05–0.08 ms/frame`, `fb_creates` dropped from `5.00/frame` to `0.00/frame`, `memo_bump[2]` was 0 during steady racing, and `submit_cpu_ms` dropped to `9.13–11.98 ms`, achieving steady ~56 FPS. The race-start dip to 41–45 FPS was investigated: an experimental attempt in Run 33 to bypass `mtl_wait` (`return 1`), enable `upload_prologue = true`, and cache all textures in `released_images` caused a `SIGSEGV` in `vulkan.adreno.so` (`offset 0x22c24c`) because `mtl_wait` must flush submissions and retire slots via `xbg_legacy_wait`. Analysis of Run 32 log (line 9941) showed the race-start dip was actually a one-time 401.8 ms compile hitch from 46 new race-start pipelines (`pipelines_new=46`), now persisted into `/sdcard/nxdroid/vk-pipeline-cache.bin` (9.11 MB) and `/sdcard/nxdroid/vk-pipeline-list.bin` (1.56 MB) for precompilation at startup via `warm::build()`. The stable configuration retains `mtl_wait_acq` non-blocking, `mtl_wait` with `xbg_legacy_wait`, `upload_prologue = false`, and `released_images` limited to render targets.
- **Run 34 telemetry and safe CPU/GPU pipelining in xbg_legacy_wait (2026-11-07):** live telemetry (`/tmp/run34_pid24283.log`) confirmed steady 3D race windows (`502–651 draws/frame`, `48 passes`) ran cleanly at `54.0–57.1 FPS` (`submit_cpu_ms = 7.86–9.10 ms`, `gpu_ms = 6.3–6.5 ms`, `legacy_wait = 0.00 ms`). During the dense 12-kart start grid (`1,226–1,287 draws/frame`, `79–82 passes`), CPU recording rose to `14.77–15.48 ms` and GPU time rose to `9.7–10.9 ms`, with `xbg_legacy_wait` blocking in `vkWaitForFences` for `9.13–12.12 ms/frame`, serializing Frame N+1 CPU recording behind Frame N GPU execution (`28.9–35.4 FPS`, `24.6–34.6 ms/frame`). Resolved cleanly in `xbg_game.cpp`: inside `xbg_legacy_wait`, after `retire_done()` and flushing in-progress recording slots (`submit_slots(false)`), `if (fence <= submitted) return 1;` returns immediately on Android. Because stream arenas snapshot CPU buffers and `recording_slot()` enforces a 2-slot ring backpressure, Frame N+1 CPU work runs in parallel with Frame N GPU execution, eliminating `legacy_wait` stalls without driver state desynchronization.
- **Run 35 crash and Run 36 locked 60 FPS milestone (2026-11-07):** In Run 35, an unconstrained `if (fence <= submitted) return 1;` was tested, but mid-frame syncs during active recording caused mid-frame slot submissions that broke active render passes, crashing with `SIGSEGV` at `vulkan.adreno.so + 0x22c24c` (`addr = 0xb4`, null subpass state in `vkCmdDrawIndexed`). In Run 36, safe 1-frame boundary pipelining was deployed in `xbg_game.cpp`: `if(t && t->pending && t->covers>=fence && !cur.pending && !(cur.recording && cur.ops)) return 1;`. Only when at a clean frame boundary with the target fence in-flight and the alternate slot free does the host return early, while mid-frame syncs and ring-full conditions fall through to synchronous waiting. Live Galaxy S23 Ultra testing achieved **60.01–60.22 FPS locked** across the dense 12-kart start grid (1,247 draws/frame), with `submit_cpu_ms = 11.90–12.56 ms`, `gpu_ms = 9.44–10.08 ms`, and `legacy_wait = 0.00 ms` with zero crashes. APK installs are permanently stabilized via persistent keystore (`~/.android-dm/debug.keystore`).
- The `[RED] … hybrid draws are not collected` line in its log is a Metal-only statistic the Vulkan replay does not collect, not a rendering fault.

## Miis

The game builds Mii heads from the console's MiiModel system data, starting at boot for the title's demo race, and lists the six default Miis for its "Select a Mii". Firmware content is not the host's to ship, so Mii heads draw nothing while bodies and favourite colours show.

- **Current: the Mii database** (`hle_mii.c`). The first boot logged `[RED] sf: the game connects to service mii:e … mii:u itself`, then aborted: `nn::mii::Database` keeps an `IDatabaseService` of the mii service at +0 (`Database::Initialize`, `sdk+0x1c5664`), and `AppendMii` / `ShowMiiEdit` start the MiiEdit applet. The host takes over the public methods: a console with no Mii of its own (an empty database: no index, nothing to update) that still has the six default Miis every console has. The game asks for those with `Get(…, 6, SourceFlag 2)` and never reads the count (`main+0x81e954`): its boot-time list of Mii icons (`main+0x419dc8`) builds a head model for each of the six, and zeroed entries failed the model's `CharInfoAccessor::IsValid` (`CharModel::Initialize` returned 0xd67e, `main+0x8f15b0`) and crashed at `main+0x8f152c`. A CharInfo the host builds is the default Mii's parameters with Switch common colours, a create ID with version 4 and variant bits (fixed per default Mii, so a saved choice finds the same Mii; fresh for `BuildRandom`, which the title's demo race calls for 12 racers) and the nickname "no name"; every field is within `CharInfoRaw::Verify`'s ranges (`sdk+0x1b68c8`). The Mii editor is cancelled (0xE7E, which `ShowMiiEdit` itself treats as success).
- **Current: the MiiModel stand-in** (`dm_mii_standin` in `hle_mii.c`, mounted by `hle_fs.c` `MountSystemData`; any other system data answers "target not found"). The game aborted in `fs::detail::GetFileSystemProxyServiceObject` under `fs::QueryMountSystemDataCacheSize` (`main+0x8f23bc`): it mounts system data 0100000000000802, MiiModel, as `MiiResource:` and reads `NXTexture{Low,Mid}{Linear,SRGB}.dat` and `Shape{Mid,High}.dat` whole; the SDK's Mii rendering is linked into `main` (`main+0x8f1400`–`+0x8fc000`). The host writes a stand-in of the same layout with every part empty. The layout as the code reads it:
  - texture file: +0xc the largest decompressed size of each of 11 part kinds, +0x38 their alignments, from +0x64 one 0x1c-byte entry per part (offset, size, stored size, 4 zlib parameters, then width, height, format, mips);
  - shape file: +0xc / +0x3c the same for 12 kinds, from +0x6c one 0x58-byte entry per part (offset, size, stored size, parameters, five vertex attribute offsets and sizes, index offset and byte size, bounding box), then hair (132 × 0x48, +0x12704) and faceline (12 × 0x24, +0x14c24) transforms.
  - A texture of size 0 is skipped (`main+0x8faaf4`). Shapes cannot all be absent, because the faceline is drawn without a check (a null buffer read at `main+0xa690d0` under `main+0x8286c4`), so every shape entry points at one shared mesh of one vertex and the triangle (0, 0, 0), 32 bytes of zeros in a stored zlib block. The largest sizes must not be 0: they size the model's memory pool (`main+0x8f2e6c`), whose alignment is the first one.

## Files and saves

- **Resolved: SIGSEGV in `crypto::detail::CbcModeAes128Helper::DecryptBlocks` with a null destination** (`main+0x8737e8`, right after `aoc:` is mounted). The add-on content (0100152000023001: `contents.dat` and `version.txt`; the courses are in the update) is decrypted in `AocHeap`, a 0x3130-byte heap that also holds the mount cache. The host answered `QueryMountAddOnContentCacheSize` with 4 KB, and the 0x1400-byte decryption buffer then did not fit. On Horizon the cache is the RomFS's file table as `RomFsFileSystem::GetRequiredWorkingMemorySize` sizes it: both hash tables (4 bytes a bucket, the builder's bucket count) and all directory and file entries (0x18 / 0x20 bytes plus the name, padded to 4), 0x88 bytes for these two files. The host computes that from the folder it mounts (`romfs_work_size` in `hle_fs.c`); `rom` keeps its minimum answer, which is too small rather than too large.
- **Resolved: every boot asked to pick a Mii again** (`DM_FS=1`: `UserSave:/userdata.dat` not found although the host save had it). The game mounts `CommonSave` with `MountDeviceSaveData` and `UserSave` with `MountSaveData(uid)` (`main+0x8b0c84`), two saves on Horizon; the host made device save data the account save (for Animal Crossing: New Horizons, which mounts only device save data), so both names shared one directory. At boot the save manager deletes `CommonSave:/userdata.dat` (`main+0x8b1910`, through its file device's `DeleteFile`, `main+0x633afc`; a probe there with `@*x1+8` shows the name) and commits, and in the shared directory that was the account save's own file. A game whose `main` imports `MountSaveData` too now gets its device save as `<DM_SAVE>_device`, a transaction of its own (`hle_fs.c`); of the games on hand only this one imports both.
- `romfs_marker` is `UI/cmn/movie/StaffCredits.mp4`.

## Audio

- **Resolved: an incomplete first command list permanently selected the wrong header layout.** The reproducing test from [PR #331](https://github.com/seedds/nxnative/pull/331) fails on the old host and produces stereo PCM with the fix; the PR author reports sound on the Mac with 4.0.1. Local validation uses synthetic command lists because this machine has no Mario Kart Mac build. See [Incomplete startup lists must not select the command layout](../../../docs/reference/audio.md#incomplete-startup-lists-must-not-select-the-command-layout).
- **Resolved: no sound; `[RED] audren: no DeviceSink (ID 0x10) in the command list, 0 commands of 0x148 bytes`.** SDK 4's command list has SDK 6's header, but its DeviceSink (`CommandBuffer::GenerateDeviceSinkCommand`, `sdk+0x19e690`) is ID 0xf and 0x130 bytes: device name +0x14, upsample buffer +0x118, input count +0x120, input indices as bytes from +0x124. `capture` takes the one 0x130-byte command with 1 to 6 inputs when there is no 0x148-byte one (`g_sink4` in `hle_audren.c`).
- **Resolved: the update lock.** Its `AudioRenderSystem::Update` (`sdk+0x19b77c`) locks an `nn::os::MutexType` at +0x1d0, not SDK 16's `SdkMutexType` at +0x1f0. The host took SDK 16's for every SDK before 20, which wrote a lock word into another field and excluded nothing; this was the first game it was plainly wrong for. `update_lock` in `hle_audren.c` now reads it off each SDK's own `Update`.

## Rendering

- **Resolved: a 2D array in a cube slot.** As a race loads, the game binds a one-layer 2D array (format 0x44) at slot 10 of two pixel shaders that declare a cube there, and it was bound as is (`texture type mismatch … declares slot 10 as Metal type 5, texture … is type 3`). The zero cube is now bound for a 2D array of fewer than six layers in a cube slot (`tex_fit`).
- The race records conditional rendering as a course loads; `render_cond on` evaluates it at replay.
